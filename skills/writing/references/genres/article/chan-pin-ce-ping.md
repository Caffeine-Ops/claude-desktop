# 文章 · 领域：产品 / 工具评测

> 本文只写「产品 / 工具评测在 [`core.md`](./core.md) 之上，额外要注意什么」，不重复 core 的通用方法论。分流、骨架、钩子、论据四等级、七轮扫描、读者评分团都在 core，本文假设你已读过。

评测大多是**说明介绍型**为主、末尾带一个判断——你要让读者搞懂「这东西怎么样、适不适合我」。它的特殊风险是**信任**：评测这个体裁天生活在「你是不是收了钱」的怀疑里，一旦读者觉得你屁股歪了，写得再详实也白搭。所以评测在 core 之上，第一位不是写作技巧，是**利益披露**这条硬红线。结构上评测常配 [问答式](../../structures/article/wen-da-shi.md)（读者带着一串「贵不贵 / 好不好上手 / 适合我吗」来）或 [层层递进](../../structures/article/ceng-ceng-di-jin.md)。

---

## 目标定义

core 要求说明型写下「读者应该会 / 搞懂什么」。评测把落点收窄成一句话：**让读者做出「我到底该不该用它」的决定**。注意——不是「让读者知道它好」，是「让读者判断它适不适合**自己**」。

- ✅ 「读完这篇，你能判断出这个工具适不适合你的场景，以及如果用、要注意什么坑。」
- ❌ 「读完这篇，你会知道这个工具有多强大。」——这是软文的落点，不是评测的。

判据：我这篇的落点，是帮读者**做决定**，还是帮产品**做宣传**？后者 → 你写的不是评测，是广告，请改标题别骗读者。

---

## 结构要点

### 硬红线：利益披露

**这是评测不可逾越的第一条。** 只要你和被测产品有任何利益关系，**必须在文章显眼处（开头或结尾，不能藏）主动说明**：

- 是否收了厂商的钱（推广费、广告费）。
- 是否是厂商送测 / 免费提供的样品或账号。
- 是否有返利、分成、合作关系。

**为什么是红线**：评测的全部价值建立在「读者相信你是中立的」之上。瞒下利益关系写「客观评测」，是欺骗；被发现，你这个作者的所有评测一起失去可信度。**披露不丢人，瞒才丢人**——大方说清「这是厂商送测的，但下面的话我按自己用的感受写」，读者反而更信你。

- ✅ 「先说清楚：这个账号是厂商免费给的。但下面的优缺点，我按自己真实用下来的写，该说不好的地方一样说。」
- ❌ （收了钱却）通篇「客观第三方评测」，只字不提利益关系。

> 这条和 shared-standards §6 的事实红线同级：那条禁止编造数字，这条禁止隐瞒立场。两者都是「不能骗读者」的底线。

### 对比维度：先声明，再逐项走

评测的主体是「比」——和什么比、比哪几项。铁律：**先把对比维度一次性声明清楚，再逐项走完，每一项对所有对比对象都要走到。** 不能想到哪比到哪、也不能只在对自己观点有利的维度上比。

顺序：① 先声明「本次从这 N 个维度评测：性能 / 价格 / 上手难度 / 生态……」→ ② 逐维度走，每个维度下把被测对象都过一遍 → ③ 最后汇总。

**常见走样**：① 维度不声明，东比一句西比一句，读者拼不出全貌；② 只挑对某个产品有利的维度比（在它强的地方大书特书，它弱的地方绝口不提），这是隐性偏袒；③ 维度声明了却没走全（说好比五项，实际只详写了两项）。

### 「适合谁 / 不适合谁」比「好不好」有用

评测最没用的结论是「它很好 / 它不好」——因为**没有绝对的好，只有适不适合**。一个工具对老手是神器、对新手是灾难。所以评测的落点应该是一张**「适配表」**而非一个「打分」：

- ❌ 「综合评分 8.5，推荐购买。」——8.5 对谁而言？推荐给谁？
- ✅ 「**适合**：需要批量处理、且能接受一点学习成本的团队。**不适合**：偶尔用一次、图省事的个人——对你它太重，装它的功夫够你手动干完了。」

「适合谁 / 不适合谁」逼你把「好不好」拆到具体人群和场景上，这才是读者真正要的——他要的不是你的分数，是「**我**这种情况该不该上」。

## 写作手法

### ① 给可复现的测试条件

评测里每一个结论（尤其性能、速度、效果类），都要**交代你是在什么条件下测出来的**，让读者能复现、能判断这个结论对他的场景成不成立。

- ❌ 「这个工具处理速度很快。」——多快？测的什么？什么机器？读者没法判断对自己快不快。
- ✅ 「我拿它处理同一批 500 张 4K 图（MacBook Air M2 / 16G 内存），平均每张 1.2 秒；换成 100MB 的大文件就明显吃力了，单个要 20 秒开外。」（测试样本、硬件环境、结论、以及边界都给了）

可复现条件是评测的「一手数据」（core 论据四等级里的最高级）。给了条件，你的结论就从「你说的」变成「他能验的」，信任度直接拉满。没给条件的性能结论，等于形容词。

### ② 优点要给场景，缺点要给分寸

- **写优点**：别停在形容词（「很强大」「体验好」），落到「在什么场景下、帮你省了什么」。「它的批量重命名，我一次改 300 个文件名只花了 10 秒——以前手动得半小时」比「功能强大」有用一百倍。
- **写缺点**：这是评测信任度的试金石。**一个只有优点的评测，读者默认它是软文。** 主动写出真实缺点、且给分寸（这个缺点对谁是致命的、对谁无所谓）——「它没有中文界面，英文不好的会难受；但如果你本来就习惯英文工具，这不算事」。**敢说缺点、且说得有分寸，是评测最强的信任状**（呼应 core 的「反方处理」和微信手册的「自曝其短」）。

### ③ 区分「事实」和「我的偏好」

评测里混着两种话：客观事实（「它不支持导出 PDF」）和主观偏好（「它的界面我不喜欢」）。**必须让读者能分清哪句是事实、哪句是你的口味**——因为你的口味不一定是他的。

- ✅ 「它默认是深色界面，不能切浅色（**事实**）。我个人不太习惯，但这纯属偏好，你可能正好喜欢（**偏好**）。」

把偏好诚实标成偏好，读者能自己判断「这条对我算不算缺点」——这比你替他下结论有用。

## 自检清单

在 core 自检清单之外，产品评测额外逐条勾：

- [ ] **利益披露到位**：收费 / 送测 / 返利 / 合作关系已在显眼处主动说明，没有隐瞒（硬红线）。
- [ ] 落点是帮读者「做决定」，不是帮产品「做宣传」——标题和内容都对得上「评测」二字。
- [ ] 对比维度先声明再逐项走，每个维度对所有对象都走到了，没只挑有利维度比。
- [ ] 结论落到「适合谁 / 不适合谁」，不是一个笼统的「好 / 不好」或孤立分数。
- [ ] 每个性能 / 效果类结论都给了可复现的测试条件（样本、环境、以及失效边界）。
- [ ] 真实写了缺点、且给了分寸（对谁致命、对谁无所谓），不是通篇优点。
- [ ] 客观事实和主观偏好做了区分，没把「我不喜欢」当成「它不好」硬塞给读者。
- [ ] 涉及的每个数字（价格、速度、参数）真实可溯源，拿不准的标了【待核实】。

## 改写诊断要点

沿用 core 的七轮扫描 + 读者评分团，产品评测**先过一道红线闸、再进七轮**：

**红线闸（改之前先查，不过直接打回）**：有利益关系却没披露 → 补披露，或这篇根本不该以「客观评测」发。

七轮扫描里额外重点盯：

- **第 4 轮 · 举证**：每个性能 / 效果结论查「有没有给可复现条件」，没有的补测试环境，或降级为「我的主观感受」。
- **第 7 轮 · 消除读者犹豫点**：站在「不同场景的读者」角度扫——新手读者会不会被吓退、老手会不会觉得太浅、预算敏感的读者关心的价格有没有讲清。
- **读者评分团**里**「怀疑论者」专问一句**：「这篇是不是软文？」——如果通篇没缺点、没利益披露、结论是笼统好评，基本就是。让这个身份把评测拉回中立。

> 产品评测诊断的一句话抓手：**把文章递给一个正打算掏钱、又怕被坑的读者——他读完能不能判断出「适不适合我、有什么坑、你有没有立场」。三个都答得上，才是一篇合格评测。**
