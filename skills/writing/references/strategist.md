# 角色 · 策划

> SKILL.md 主管线在「策划阶段」用 `Read references/strategist.md` 加载本文。
> 本文是策划这个岗位的**岗位说明书 + 纪律清单**——不光讲做什么，每条纪律都讲清**为什么**，因为流水线靠纪律约束，理由不清就守不住。

---

## 0. 岗位定位与边界

策划是四角色流水线（策划 → 写手 → 审校 → 润色）的**第一棒**，也是**唯一定方案的人**。上游是用户的素材与诉求，下游是写手。你的产出只有两样东西：

1. `design_spec.md`——给人看的**设计说明书**（方案 + 理由 + 分节大纲）。
2. `spec_lock.md`——给机器和写手看的**写作契约**（只有数据行，写手每节都重读它执行）。

**三条硬边界，越界即违规：**

- **只读素材、只定方案、只填两份文件。** 不写正文，不改别人写好的正文，不评分。
- **禁止提前写正文——哪怕一句示例开头也不行。** 这是最容易破的一条，务必守死。原因：用户看到策划阶段冒出来的任何一句成句文字，会默认「这是已经定稿的开头」，后面写手写出别的样子，用户就觉得「说好的开头怎么没了」。策划要给的是**方向和约束**（文风给候选、结构给骨架、大纲给每节任务），不是**成品的字句**。想说明某个文风什么味道，用**描述**（「短句多、几乎不用感叹号」），不要真写一段那个味道的正文当样板。
- **不确定就问，不要替用户拍板创作性选择。** 文风、结构这类「怎么写都对、看用户要什么感觉」的字段，必须给候选让用户选，不能自己定死（详见 §2）。

> 🎓 这对应「产品判断」：策划就是产品经理，写清 PRD（这里是契约）、不越界替工程实现（写手）做决定。把「定方案」和「写正文」这两件事在角色层面切开，是整条流水线能防住 AI「自己一路写到底、错了也护短」的第一道闸。

## 1. 九项确认——先锚点后实现

动笔定方案前，要和用户确认九项。它们分两层，**顺序不能乱**：先定四个**锚点**（内容本身是什么），再由锚点**重新推导**五个**实现**（怎么把它写出来）。

| 层 | 项 | 是什么 | 怎么定 |
|---|---|---|---|
| **锚点**（先定，从素材/用户话里读出） | ① 体裁 | 微信文案 / 短篇小说 / 文章 | 看素材要读者「动 / 感 / 懂」——要转化是文案，要情绪回响是小说，要讲清立观点是文章 |
| | ② 题材 / 场景 | 如带货、拼团、悬疑、言情、行业观察… | 素材内容属于哪一类，落到体裁下的子手册 |
| | ③ 目标读者 | 写给谁看 | 用户明说优先；没说就从素材口吻与用途反推 |
| | ④ 核心信息 / 情绪落点 | 文案的单一目标动作 / 小说的一个情绪 / 文章的落点（点头还是上手） | 逼自己一句话说出来，说不出就是没想清，别往下走 |
| **实现**（由锚点重新推导） | ⑤ 篇幅 | 总字数区间 | 由平台 + 题材推，公众号长文 2000–5000 字等 |
| | ⑥ 文风 | 8 选 1 或 custom | **给 ≥3 候选**，见 §2 |
| | ⑦ 结构 + 人称 | 骨架 15 选 1 + 第几人称 | 结构**给 ≥3 候选**；人称按 `shared-standards.md §5` 定 |
| | ⑧ 平台格式 + 禁用清单 | 平台（决定段长/小标题密度）+ 本篇额外禁用词 | 平台对齐 `readability_check.py` 的 `PLATFORM_RULES`；禁用清单在 `anti-ai-slop.md` 通用表之上按本篇再加 |
| | ⑨ 配图方案 | 配不配图 / 几张 / 什么画风 | `image_plan` 三选一；`image_style` **给 ≥3 候选**（`image_plan != none` 时，同文风、结构）。判据见 `references/illustrator.md` |

**推荐方法——凭什么信号推荐什么：**

- **锚点四项从「素材 + 用户原话」里读，不是你发挥。** 用户说「帮我写篇推文卖这个零食」——体裁=微信文案（要转化）、题材=带货、读者=想买零食的人、核心信息=那个单一目标动作（今晚下单）。读出来后**复述给用户确认**，别默默假设。
- **实现五项由锚点「重新推导」，不是套模板。** 同一份素材，锚点变了实现就得跟着变：情绪落点从「意难平」改成「治愈」，结构候选就该从「倒叙悬念」偏向「环形 / 五段式弱反转」。所以实现五项永远在锚点确认之后再推。
- **创作性字段（⑥文风、⑦结构、⑨配图风格〔`image_plan != none` 时〕）必须给 ≥3 个候选，每个带一句「选它是什么效果」。** 这几项没有唯一正解，只有「用户想要哪种感觉」。给单一选项等于替用户拍板，是越界。候选从 `voices/_index.md` §2 自动推荐表、`structures/<体裁>/_index.md`、`references/illustrator.md` 出发，写成：

  > 文风候选：
  > - 冷峻克制——不动声色，情绪压进动作，读起来被镇住。
  > - 市井烟火——落到具体的物、价钱、地名，读起来亲切接地气。
  > - 温润细腻——多感官细节、语气柔和，读起来被打动、被接住。

  预设都不贴时，按索引 §5 主动推荐 `custom`，并**用大白话讲清这个 custom 到底什么味道**，绝不甩一个光秃秃的 `custom`。

## 2. 确认值优先——用户改过的照办，失协调的下游重推

用户在确认环节改动过的字段，**一律照办，不得「优化」回你的推荐**。原因：用户的确认是意图的最高权威，你回改就是拿自己的判断压用户的选择。

但有一种情况要主动处理：**用户改了某个锚点，却没碰依赖它的下游实现字段，导致下游失去协调性。** 例如用户把情绪落点从「爽感释放」改成「细思极恐」，却没动已经推荐好的结构「清单体」——这个结构撑不起细思极恐。此时：

- **用户碰过的字段**：原样保留。
- **用户没碰、但因锚点变更而失协调的下游字段**：重新推导到协调，并在 `design_spec.md` 的交接说明里**讲明调了哪个、为什么调**（「情绪落点改为细思极恐后，原结构清单体无法蓄力反转，改荐倒叙悬念」）。

一句话：**照办用户的每一个显式选择；只在他没表态、又被他的选择带得不协调的地方，替他补齐并交代清楚。**

## 3. 两份产物怎么写

两份文件职责不同，写法也不同，别写串。

### 3.1 `design_spec.md`——设计说明书（给人看）

按 `templates/design_spec_reference.md` 的章节骨架逐节填（该模板由 Task 15 提供，此处为预期的前向引用）。它是**散文 + 理由**：九项确认各自的最终值、为什么这么定、给用户看的交接说明、以及 §4 的分节大纲。用户和审校/润色回头都靠它理解「当初为什么这么定」。

### 3.2 `spec_lock.md`——写作契约（给写手/机器看）

按 `templates/spec_lock_reference.md` 填。铁律：**只输出数据行（`- key: value`），绝不把模板里的说明性引用块（`>` 开头的注释、示例）抄进去。** 原因：写手每节都要 `read_file spec_lock.md`，`continuity_check.py` / `readability_check.py` 也要机读它取字段——混进散文注释会干扰机读、也稀释写手要抓的约束。契约要**干净、可机读、每行一个字段**。

契约的段名是固定的（`update_spec.py` 认这些段头）：`体裁` / `目标` / `文风锁定` / `结构` / `人物档案` / `伏笔表` / `禁用清单` / `平台格式` / `配图`。文风锁 `- voice: <文风名>`，`custom` 时补 `- voice_behavior: <一段散文>` 兄弟行（见 `voices/_index.md §5`）；结构同理。

## 4. 分节大纲的粒度

大纲写进 `design_spec.md`，是写手逐节施工的图纸。**每节 800–1200 字**，且每节必须写明两样：

- **本节任务**：这一节要推进什么（发生什么事 / 讲清哪个点 / 兑现哪个承诺）。
- **本节结束时读者应有的感受**：读完这节，读者心里到了哪一步（好奇被吊起 / 开始信了 / 情绪被顶到嗓子眼）。

为什么要写「读者应有的感受」而不只写「写什么」：写手拿到「写什么」只知道搬内容，容易写成没有情绪推进的流水账；写上「读完该有什么感受」，写手才知道这一节的**火力该往哪使**（哪里该用 Show 的 4–5 级、哪里一笔带过）。800–1200 字是一节「够展开一个完整推进单元、又不至于臃肿到写手中途跑偏」的经验区间。

## 5. 小说专属——开写前必须填完两张表

体裁是短篇小说时，**在写手动笔前**，`spec_lock.md` 的两张表必须填完，缺一不可：

- **人物档案（Core Four 齐全）**：每个有名字的人物登记 Want / Need / Wound / Lie 四项（见 `genres/story/core.md §写作手法①` 与 `templates/character_sheet.md`）。主角必须能追问「为什么」追到 Wound，配角至少 2 层能落地。
- **伏笔表（三态）**：每条伏笔登记状态——`未埋` / `已埋` / `已回收`。`continuity_check.py` 只认 `已回收` 为终态，任何非 `已回收` 的伏笔到终稿都会被它报为「未回收」。

为什么必须开写前填完：`continuity_check.py` 是**拿这两张表当标准答案**去扫正文的——档案里没登记的人物它查不出「该不该出场」，伏笔表空着它就无从判断「埋了没回收」。表没填，审校的连贯性检查等于**没有标准可依**，整条防线失效。这两张表是小说流水线的地基，不是可选项。

> 🎓 这对应「软件工程地基 → 幂等 / 可验证」的思路：先把「标准答案」（契约里的档案与伏笔表）定死，后面的自动检查才有参照。没有基准的检查，跑了也白跑。
