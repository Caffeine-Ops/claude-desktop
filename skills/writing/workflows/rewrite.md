# 改写工作流（Rewrite）

> 独立工作流。触发：用户**给出一篇已经写好的稿子**，要求「改写 / 改一下 / 换个说法 / 帮我改改 / 换成小红书 / 压到 800 字 / 去掉 AI 味」。它不走主管线的「策划 → 写作」（稿子已经有了），而是走「诊断 → 定向改写」。改写和从零创作最大的区别：**必须以用户原稿为地基，标注每一处改动、说清为什么改，让用户能逐条对账**——不是推翻重写一版新的塞给他。

**前置**：先跑一次 Python 自举（见 SKILL.md 顶部「🐍 Python 环境」），把本文里所有 `$WRITING_PY` 备好。没自举，脚本全跑不起来。

---

## Step 0 · 两条路径分流（先判别，别一上来就诊断）

改写有两种来法，先看用户这句话属于哪种，**判错会白干**：

> **两种来法**：① 用户**绕过入口、直接在对话里**提改写要求 —— 走下面的意图判别（路径 A/B）；② 从 [优化已有作品](optimize-existing.md) 主入口的确认硬门**路由进来** —— 意图与档位**已经确认**，无需再判别，按带过来的档位直接执行：
> - **标准优化** → 走**路径 B（定向改写）**，并把「**整体结构不可改、允许拆分/合并段落、个人表达保留**」写入本次修改约束；
> - **深度改写** → 走**路径 A/全量**，把用户点名的「**必须保留项** + 个人表达」写入约束，本工作流自身的硬确认仍然保留。
>
> 下面的 Step 0 判别只适用于来法 ①。

| 用户怎么说 | 属于 | 走哪条路 |
|---|---|---|
| 「帮我改一下」「改改这篇」「优化下」「读着别扭你看看」——**没给具体方向** | 全套诊断 | 路径 A |
| 「改口语点」「压到 800 字」「换成小红书」「去掉 AI 味」「标题再狠点」——**给了明确、可执行的方向** | 定向改写 | 路径 B |

**判别规则（一句话）**：用户的要求里有没有一个**能当场执行、改完能验收**的方向？有 → 路径 B；没有、只是笼统说「不好，你改」→ 路径 A。

- **路径 B 直改**：用户已经指明了要什么，再拉一遍全套体裁诊断是浪费他时间——他要的是「口语化」，你却端上一张五维分报告，答非所问。**直接按方向改，改完标注改动即可**（跳到 Step 4，但 Step 3 的诊断只围绕用户那个方向做轻量版）。
- **路径 A 全诊断**：用户自己都说不清哪不好，那就得系统地替他查一遍到底哪不好——走下面 Step 1 → 4 全套。
- **拿不准**：一句话反问确认（「你是想我整体把把关，还是有具体方向比如改口语 / 压字数？」），别自己猜。方向类要求最忌讳猜错。

> 🎓 [产品判断 · AI 体验设计] 这就是「别用重流程解决轻需求」。同一个「改写」入口，用户的意图重量差很多：一个要体检，一个要理个发。识别意图轻重、给匹配的流程，比无脑上最全的流程更专业。

## Step 1 · 落项目、把原文收进 sources/（路径 A）

改写也要有项目目录，产物才不散落。先看 cwd 定 `--dir`（规则同 SKILL.md Step 2）：

```bash
pwd
$WRITING_PY ${SKILL_DIR}/scripts/project_manager.py init <项目名>-改写 --dir <解析好的目录>
```

**原文进 `sources/`**（原稿是这次改写的唯一地基，必须留档，改完好对照）：

```bash
# 用户贴在对话里 → 存成 sources/original.md
# 用户给的是 PDF / Word / 网页 URL / txt 文件 → 先转 Markdown
$WRITING_PY ${SKILL_DIR}/scripts/source_to_md.py <原文文件或URL> --out-dir <项目>/sources
```

## Step 2 · 识别体裁与题材（识别不出就问，别硬猜）

不同体裁的诊断法完全不同（文案查转化、小说查伏笔、文章查论证），**先认准体裁才能选对诊断**。照 SKILL.md 的「体裁 → 目录映射表」认：

| 看原文像什么 | 体裁（`genre`） | 题材库目录 | 结构库目录 |
|---|---|---|---|
| 推广、带货、拼团、私域、直播预告 | `wechat` | `genres/wechat/` | `structures/copy/` ← 注意是 copy |
| 有人物、有情节、要读者「感」 | `short-story` | `genres/story/` ← 注意是 story | `structures/story/` |
| 讲清一件事 / 立一个观点 | `article` | `genres/article/` | `structures/article/` |

**识别不出来就直接问用户**：「这篇你是当公众号推文 / 短篇故事 / 观察文章来改？定位不同改法差很多。」——**别硬猜体裁**，猜错了整套诊断都用错标准。题材（带货？悬疑？行业观察？）同理，认不出就问。

**判完 genre 后，立刻写一份最小写作契约**（`<项目>/spec_lock.md`），只要两行：

```markdown
## 体裁
- genre: wechat
```

段名 `## 体裁` 与字段名 `genre` 必须逐字用这一套（`update_spec.py` 认死九个固定段名），
否则后续要改契约时脚本认不出。桌面端写作工作区也读这一行决定排版皮肤——不写的话，
一篇公众号推文会被按职场公文的版式显示给用户。

（小说改写另有更高要求：`continuity_check.py` 需要完整的人物档案与伏笔表，见下面 Step 2 的
逆向补契约那条，那种情况下这份最小契约会被完整契约取代。）

## Step 3 · 三脚本 + 按体裁人工诊断，产出三级清单（路径 A 核心）

先切审校角色（改写的诊断阶段 = 审校那一棒的活，只诊断不动手）：

```markdown
## [角色切换：审校]
📖 正在加载岗位说明书：references/editor.md
📋 当前任务：诊断这篇待改写的原稿，产出 🔴🟡🟢 清单
🚧 边界：只诊断、不动手（改是下一步的活）
```

**第一步 · 跑脚本拿客观指标**（按体裁选跑，产物落 `reviews/`）：

```bash
# 所有体裁都跑 —— AI 味五维，总分 50、低于 35 是重灾
$WRITING_PY ${SKILL_DIR}/scripts/ai_slop_checker.py <项目>/sources/original.md

# 所有体裁都跑 —— 平台合规（--platform 取原文所在 / 目标平台）
$WRITING_PY ${SKILL_DIR}/scripts/readability_check.py <项目>/sources/original.md --platform <平台>

# 仅小说加跑 —— 伏笔 / 人物 / 人名连贯性（--spec-lock 必填；改写场景先据原文补一份契约再跑）
$WRITING_PY ${SKILL_DIR}/scripts/continuity_check.py <项目>/sources/original.md --spec-lock <项目>/spec_lock.md
```

> 小说改写要跑 `continuity_check.py` 得先有 `spec_lock.md`。改写场景没走过策划，就据原文**逆向补一份**契约（人物档案 Core Four + 伏笔表三态），当诊断的标准答案。

**第二步 · 按体裁跑人工诊断**（脚本查不出的判断，纯靠人，出处在各体裁 core.md 的「改写诊断要点」）：

| 体裁 | 人工诊断法 | 出处 |
|---|---|---|
| 微信文案 | **AI 痕迹仪表盘 + 转化要素缺失自检**（目标动作可否观测 / 是不是单一卖点 / 结尾是不是具体动作 / 证据是不是形容词充数） | `genres/wechat/core.md` |
| 短篇小说 | **逐场景过 GCOS**（Goal-Conflict-Outcome-Sequel 四格量每个场景，填不出 Goal/Conflict、Outcome 含糊的标「软场景」） | `genres/story/core.md` |
| 文章 | **七轮扫描**（每轮只盯一个维度：清晰度 / 语气一致 /「所以呢」/ 举证 / 具体化 / 情绪浓度 / 消除犹豫点） | `genres/article/core.md` |

**第三步 · 合并成三级清单，写进 `reviews/`**：脚本命中 + 人工诊断合并成一张 🔴（必须改）/ 🟡（应该改）/ 🟢（可以改）清单，**每条带行号 + 一句「为什么要改」，不写改法**（改法留到 Step 4）。

**⛔ BLOCKING —— 出完清单必须停下问用户**：把三级清单端给用户，明确问：**「按这张清单改吗？还是你只想改其中某几条 / 有别的方向？」** 等用户明确回复再动手。理由：改写动的是用户自己的稿子，哪些该改、改到什么程度，是他的意图不是你的判断——尤其 🟢 项（锦上添花）很可能他根本不在乎。**替用户默认「全改」就是越界。**

### 完整诊断报告样例（微信带货推文，约 2600 字）

```
【AI 痕迹仪表盘】ai_slop_checker.py 五维
| 维度       | 得分 | 判读 |
| 结构均匀度 | 5.5  | 🟡 段落长度太齐，全是四五行的段，缺换气短段 |
| 套话密度   | 8.0  | 🟢 基本干净 |
| AI句式密度 | 6.0  | 🟡 命中 2 处「不仅…还…」、1 处「既…又…」 |
| 书面腔浓度 | 7.5  | 🟢 尚可 |
| 具体度     | 4.0  | 🔴 通篇「香浓」「酥脆」形容词，几乎没有具体细节 |
总分 31 / 50 —— 低于 35。

【转化要素缺失】对照 wechat/core.md 自检清单
- 🔴 结尾行动指令是「点击了解更多」，不是可观测的具体动作。
- 🔴 全文并列吹「好吃 / 健康 / 便宜」三个卖点，焦点散了。
- 🟡 开头「说到零食，大家都不陌生」——正确的废话，没勾住。
- 🟡 无信任状，全靠自夸。

【合并 · 三级清单（进 reviews/）】
🔴 L12  砍到单一卖点：只主打「解馋不长胖」——为什么：一篇多个目标动作，选择过载，一个都不做。
🔴 L88  结尾无具体动作——为什么：转化在最后一步漏光。
🔴 L40  「香浓酥脆」纯形容词——为什么：形容词是你的判断，读者不信；具体度 4.0 拉垮总分。
🟡 L3   开头是废话——为什么：前 50 字没出现读者处境或数字，3 秒法则没过。
🟡 全篇  无信任状——为什么：承诺没证据支撑，读者不买账。
🟢 段落  节奏太齐——为什么：结构均匀度 5.5，插短句能救，但不伤转化，有余力再动。

⛔ 以上清单请你过目：按这张改，还是你只在意某几条 / 有别的方向？
```

## Step 4 · 改写、进 drafts/、逐处标注（用户点头后）

用户确认要改哪些后，切润色角色，**只按确认的清单条目改**，改完落 `<项目>/drafts/`。

> 落 `drafts/` 而不是 `output/`：`drafts/` 是「正在打磨的正文」，`output/` 是「定稿与导出物
> （.docx / .html）」——主管线本来就这么分。桌面端写作工作区只扫 `drafts/`，落错地方的
> 后果是用户跑完整条改写流程、右栏却一片空白（2026-07-31 修）。

**改写稿必须标注「改了哪里、为什么」**——这是改写和创作的分水岭，用户要能逐条对账。在改写稿末尾附一张**改动对照表**：

```markdown
## 改动对照（对账用）

| # | 原文（节选） | 改后 | 对应清单 | 为什么这么改 |
|---|---|---|---|---|
| 1 | …点击了解更多 | 点这里，今晚 12 点前拍下第二件半价 | 🔴 L88 | 换成可观测的具体动作 + 即时理由，把读者推到下单 |
| 2 | 香浓酥脆，回味无穷 | 咬下去「咔」一声，掉渣 | 🔴 L40 | 形容词换成声音+动作的 Show（见 anti-ai-slop §5），救具体度 |
| 3 | 好吃、健康又便宜 | （删「便宜」「香浓」枝节，全篇收束到「解馋不长胖」） | 🔴 L12 | 单一卖点，别让第二个目标分散焦点 |
| 4 | 说到零食，大家都不陌生 | 一到下午三点就想吃点啥，又怕晚上称重后悔—— | 🟡 L3 | 开头换成读者处境，过 3 秒法则 |
```

**改写纪律**（同润色那一棒）：只改清单上的；能删就删、其次换、最后才小范围重写；**不碰事实、观点、结构逻辑**（除非用户明确要「换结构 / 换体裁重写」——那种是大改，走完整重构，但仍要标注对照）。

> 从「优化已有作品」路由进来时，这条纪律按档位收紧：**标准优化**只允许拆合段落、绝不搬家/增删章节（整体结构不可改）；**深度改写**才可重排结构，但用户点名的「必须保留项」与「个人表达」是不可逾越的红线。

**改完重跑脚本验收**：

```bash
$WRITING_PY ${SKILL_DIR}/scripts/ai_slop_checker.py <项目>/drafts/rewrite.md
```

确认五维回到 35 以上、🔴 全清。脚本达标只是及格线，「读着顺不顺」最终靠人拍板。

**✅ 交付检查点**：

```markdown
## ✅ 改写完成
- [x] 原文已存 sources/，改写稿在 drafts/
- [x] 改写稿附了改动对照表（每处：原文 → 改后 → 对应清单 → 为什么）
- [x] 只动了用户确认的清单项，没顺手改清单外、没推翻重写（除非用户要求换体裁）
- [x] 重跑 ai_slop_checker 五维 ≥35
- [x] 报告里给出交付文件完整路径（/Users/… 或 ~/ 开头）
```
