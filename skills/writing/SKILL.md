# Writing Skill · 工程化中文写作

> 把「写一篇」拆成一条纪律严明的流水线：**素材 → 项目 → 文风学习 → 策划（八项确认）→ 查资料 → 逐节写作 → 质检 → 润色 → 导出**。核心不是「让 AI 一口气写完」，而是用**写作契约**（`spec_lock.md`）把方案钉死、让写手每写一节都重读契约，把 AI 长文写着写着就跑味、越写越套话这件事从根上堵住。

**核心管线**：`素材处理 → 项目初始化 → [文风学习] → 策划 → [查资料] → 逐节写作 → 质检 → 润色 → 导出`

> [!CAUTION]
> ## 🐍 Python 环境（每个会话最先跑一次）
>
> 本技能里每一条 `python3 ${SKILL_DIR}/scripts/...` 都必须跑在**本技能自己的虚拟环境**里，**不能**用机器上的裸 `python3`（它可能不存在，或版本太新、装不上 PyMuPDF 之类带原生轮子的依赖）。跑任何 python 命令前，先自举一次：
>
> - **macOS / Linux** —— `source ${SKILL_DIR}/bin/ensure-python.sh`
>   它会准备好 `~/.writing-skill/venv`（首次：创建 venv + `pip install -r requirements.txt`，几分钟；之后：秒过），并 `export WRITING_PY`。然后**把本文档里所有 `python3` 替换成 `$WRITING_PY`** —— 例如 `$WRITING_PY ${SKILL_DIR}/scripts/project_manager.py init …`。
>   （注意必须用 `source` 调用，不是直接执行——子进程里 `export` 出来的 `WRITING_PY` 父进程拿不到。venv 落在用户可写的 `~/.writing-skill/venv`，绝不建在 skill 目录里。）
> - **Windows** —— 跑 `${SKILL_DIR}\bin\ensure-python.cmd`，它 stdout 最后一行是 `WRITING_PY=<path>`。本会话后续用那个路径代替 `python3`。
>
> 自举若打印错误（找不到解释器 / pip 失败），**如实报告给用户并停下**——不许回退到裸 `python3`，那样依赖根本不在。

> [!CAUTION]
> ## 🚨 全局执行纪律（强制，最高优先级）
>
> **这是一条严格的串行流水线。下面八条比任何其他指令都优先，违反任何一条即为执行失败：**
>
> 1. **串行执行** —— Step 必须按序走，上一步的产物是下一步的输入。非 BLOCKING 的相邻步骤在前置门满足后可连续推进，不必等用户说「继续」。
> 2. **⛔ BLOCKING = 硬停** —— 标了 ⛔ BLOCKING 的地方必须完全停下，等用户**明确回复**再走，绝不替用户拍板。**Step 4 的八项确认就是 ⛔ BLOCKING**：AI 给出推荐后必须停、等用户确认或修改，才能往下写 `design_spec.md` / `spec_lock.md`。理由：八项确认里有文风、结构这类「怎么写都对、看用户要什么感觉」的创作性选择，替用户默认掉，等于拿 AI 的判断压用户的意图。
> 3. **禁止跨阶段捆绑** —— 不许把「策划」和「写作」这种跨阶段的事塞进一次输出一起做完。八项确认一旦落定，后续非 BLOCKING 步骤（写作 → 质检 → 润色 → 导出）可自动连推，无需再逐步等确认。
> 4. **每个 Step 有前置门（🚧 GATE）** —— 每步开头列了进入条件，进入前必须逐项核对。理由：跳过前置门（例如契约还没生成就开写）等于在没有合同的情况下施工，后面全是返工。
> 5. **禁止投机执行** —— 不许为后续步骤「预先准备」内容。**策划阶段绝不写正文，哪怕一句示例开头也不行。** 理由：用户看到策划阶段冒出来的成句文字，会默认「这是定稿开头」，写手后面写成别的样子，用户就觉得说好的开头没了。策划给的是方向和约束，不是成品字句。
> 6. **每节重读契约** —— 写手每写一节前，必须 `read_file <项目>/spec_lock.md` 把契约重新读进来。理由（务必读透）：长生成里前面写的正文越堆越多，早先读进来的契约与文风约束会在上下文里被**逐渐挤淡**（上下文压缩），而**模型对此毫无自觉**——约束失效不报错、不提示，你会「感觉自己还在按文风写」，实际第四节的味道已经飘走。唯一解法就是每节机械地重读，把约束顶回注意力最前面。
> 7. **逐节顺序生成，禁止分批打包** —— 按大纲第 1 节写完收尾 → 第 2 节 → …，一节一节推。理由：批量写时越往后契约衰减越狠、后半篇必然走味；且一次铺开没法在每节收尾时更新伏笔状态、自查字数；正文是连续推进的，后一节的情绪起点接前一节的落点，并行写必然接不上茬。
> 8. **禁止脚本批量生成正文、禁止子 agent 代写** —— 不许写 Python/Node/shell 脚本或套模板批量吐正文，也不许把某节委派给子 agent 写。理由：脚本生成的必然是均匀、套话、AI 味拉满的东西（正是 `anti-ai-slop.md` 全力要消灭的），完全无视文风与情绪推进；子 agent 读不到这里的完整约束链与前文，写出来风格、人称、伏笔全对不上，等于换了个没交接的人来写。跨节一致性依赖逐节带完整上文创作，脚本和子 agent 都复现不了。

## 资源库索引

三个查询入口。**先从索引挑，锁定后只读锁定的那一份，禁止 glob 整个目录。** 原因：glob 会把八种文风 / 十五种结构 / 十几个题材一次性灌进上下文，既噪声大又稀释真正锁定的那一份的约束。

| 库 | 查询入口 | 里面是什么 |
|---|---|---|
| 文风库（8 种，管「什么味道」） | `references/voices/_index.md` | 冷峻克制 / 市井烟火 / 戏谑幽默 / 文艺抒情 / 硬核干练 / 温润细腻 / 口语唠嗑 / 学术严谨 |
| 结构库（按体裁分三组，管「怎么组织」） | `references/structures/_index.md` → 再进体裁那一组子索引 | 小说组 5 / 文案组 5 / 文章组 5 |
| 体裁库（三体裁 × 细分场景，管「写给什么读者、要给什么价值」） | `references/genres/<体裁目录>/_index.md` | 每组先读 `core.md`（通用方法论）再读锁定的那一份场景手册 |

> **文风 ≠ 结构 ≠ 体裁，三把锁正交、各锁各的、任意组合。** 一篇带货推文 = 微信体裁 + PAS 结构 + 亲切口语文风。锁其中一把时别顺手把另外两把也定了。

职场写作走的是另一套资源、不进上面这套三把锁：另有独立骨架卡组 `references/workplace/`（6 张，由 `workplace-writing.md` 工作流锁用）与根级标准 `references/workplace-standards.md`（职场失礼自检表），不走三体裁的文风 / 结构 / 体裁三把锁。

## ⚠️ 体裁 → 目录映射表（关键，务必照此拼路径）

三体裁的 `genre` 值、题材库目录、结构库目录**三者命名不完全一致**。写手 / 策划读手册时，**必须查这张表拼目录，绝不能把 `spec_lock.md` 里的 `genre` 值直接当目录名**：

| `genre` 值（契约的 genre 字段） | 题材库目录 | 结构库目录 |
|---|---|---|
| `wechat` | `references/genres/wechat/` | `references/structures/copy/` ← **注意是 copy 不是 wechat** |
| `short-story` | `references/genres/story/` ← **注意是 story 不是 short-story** | `references/structures/story/` |
| `article` | `references/genres/article/` | `references/structures/article/` |

- 读锁定的题材手册：`references/genres/<题材库目录>/<sub>.md`（先过同目录 `core.md`）。
- 读锁定的结构手册：`references/structures/<结构库目录>/<structure>.md`。
- 两个最容易踩的坑：`genre: wechat` 的结构在 **`structures/copy/`**；`genre: short-story` 的题材在 **`genres/story/`**。直译目录名必然找不到文件。

## 角色切换协议

四角色流水线（策划 → 写手 → 审校 → 润色）每一棒各有边界，**切换角色时必须先 `Read` 对应岗位说明书，并显式打出切换标记**，让每一棒清楚自己此刻只能做什么、不能做什么：

```markdown
## [角色切换：审校]
📖 正在加载岗位说明书：references/editor.md
📋 当前任务：<一句话说明这一棒要干什么>
🚧 边界：只诊断、不动手（改文字是润色的活）
```

四棒的边界一句话各是：**策划**只定方案填两份文件、绝不写正文；**写手**只逐节写正文、不改契约不自评；**审校**只诊断产出问题清单、不动手改；**润色**只按清单定向改、不推翻重写不改事实。这一刀刀切开，是整条流水线「让 AI 别自己写自己评、错了也护短」的关键。

## 选区改写响应协议（桌面端工作区触发）

用户在桌面端的写作工作区里选中一段文字发起改写时，你会收到一条**带固定格式要求**的消息：
它包含本节全文、选中的那一段、用户的要求，并要求你把结果包在一对标记之间。

收到这类请求时：

1. **把改写后的文字包在这对标记之间**，标记各占一行，中间只放正文——不要解释、不要加标题、
   不要重复原文：

   ```
   ===改写结果开始===
   （改写后的正文）
   ===改写结果结束===
   ```

2. **不要修改任何文件。** 你手上有 Edit / Write 工具，但这一轮**绝对不能用**。

   > 理由：改写结果要先给用户看「原文 vs 改后」的对照，由他点「应用」才落地。你若直接改盘，
   > 用户点「放弃」时内容已经被覆盖，这一步的保护就形同虚设。落地由应用侧完成。

3. 只改选中的那一段，不要顺手改选区之外的内容——用户只授权了这一段。

4. 改完可以在标记之外用一句话说明改了什么（那句话只进聊天，不会进文档）。

### Step 1 · 素材处理（可选）

🚧 **GATE**：无（用户给了素材就做，没给就跳到 Step 2）。

用户给的是非 Markdown 素材（PDF / Word / 网页 URL / 纯文本文件），先转成 Markdown：

**✅ 检查点**：
```markdown
## ✅ Step 1 完成
- [x] 素材已转为 Markdown（或用户直接在对话里给了文字 / 无素材）
- [ ] 进入 Step 2 建项目
```

### Step 2 · 项目初始化

🚧 **GATE**：Step 1 完成或跳过；素材就绪（Markdown 文件、对话里的文字、或口头需求皆可）。

**始终显式传 `--dir`，别用裸命令。** 不传 `--dir` 时会默认落到 `${SKILL_DIR}/scripts/../projects`，产物埋在 skill 内部目录里用户找不到。先看清 cwd 再定：

```bash
pwd   # 先看，别假设
```

- **cwd（或任一父段）以 `.` 开头**（如 `~/.cowork`、`~/.claude`）→ 传 `--dir "$HOME/writing-projects"`。
- **否则** → 传 `--dir "$(pwd)/projects"`（和默认落点一致，但显式，选择在 transcript 里可见）。

```bash
$WRITING_PY ${SKILL_DIR}/scripts/project_manager.py init <项目名> --dir <解析好的目录>
```

产物：`<项目>/`（目录名 = `<slug>_<日期>`），内含五个固定子目录——`sources/`（原始素材 + 转好的 Markdown）、`analysis/`（机器提取的事实）、`drafts/`（初稿分节，一节一文件）、`reviews/`（质检报告）、`output/`（定稿与导出），以及 `README.md`。

**✅ 检查点**：
```markdown
## ✅ Step 2 完成
- [x] 项目目录建好，解析后的 <项目路径> 无 `.` 开头的段
- [x] 素材已放进 sources/
- [ ] 进入 Step 3（有往期文章）或直接 Step 4
```

### Step 3 · 文风学习（条件触发）

🚧 **GATE**：用户提供了自己的往期文章、并希望新稿贴合本人文风。没有则跳过。

先读岗位/工作流说明：详细流程走独立工作流 [`workflows/style-learn.md`](workflows/style-learn.md)（Task 17 提供，此处引用即可）。核心命令：

```bash
$WRITING_PY ${SKILL_DIR}/scripts/style_profile.py <往期文章文件或目录> --out <文风档案.md>
```

> ⚠️ **`--out` 必须落在被扫描目录之外**（项目外 / 独立路径，如 `$HOME/writing-style/<某人>.md`），**绝不能落在被扫描的往期文章目录里**。否则下次重跑，脚本会把上次生成的档案当成往期语料再统计一遍，越滚越偏。

产出的档案末尾有一段可直接抄进 `spec_lock.md` 的契约字段行，Step 4 策划时取用。

**✅ 检查点**：
```markdown
## ✅ Step 3 完成
- [x] 文风档案已生成，--out 落在被扫描目录之外
- [x] 档案末尾的契约建议行留待 Step 4 取用
- [ ] 进入 Step 4 策划
```

### Step 4 · 策划（⛔ 八项确认，不可跳过）

🚧 **GATE**：项目已初始化（`<项目>/` 存在）。

先读岗位说明书：
```
Read references/strategist.md
```

> ⚠️ **强制门**：写 `spec_lock.md` 前，策划必须先 `read_file templates/spec_lock_reference.md`（契约骨架）与 `templates/design_spec_reference.md`（设计说明书骨架），照其结构填。

**八项确认分两层，顺序不能乱：先定四个锚点（内容本身是什么），再由锚点重新推导四个实现（怎么把它写出来）。**

| 层 | 项 | 是什么 | 怎么定 |
|---|---|---|---|
| **锚点**（先定，从素材 / 用户原话里读出） | ① 体裁 | 微信文案 / 短篇小说 / 文章 | 看素材要读者「动 / 感 / 懂」——要转化是文案、要情绪回响是小说、要讲清立观点是文章 |
| | ② 题材 / 场景 | 带货、拼团、悬疑、言情、行业观察… | 内容属于哪一类，落到体裁下的子手册 |
| | ③ 目标读者 | 写给谁看 | 用户明说优先；没说就从素材口吻与用途反推 |
| | ④ 核心信息 / 情绪落点 | 文案的单一目标动作 / 小说的一个情绪 / 文章的落点 | 逼自己一句话说出来，说不出就是没想清，别往下走 |
| **实现**（由锚点重推，不是套模板） | ⑤ 篇幅 | 总字数区间 | 由平台 + 题材推 |
| | ⑥ 文风 | 8 选 1 或 custom | **给 ≥3 候选**（见下硬规则） |
| | ⑦ 结构 + 人称 | 结构 15 选 1 + 第几人称 | 结构**给 ≥3 候选**；人称按 `shared-standards.md §5` 定 |
| | ⑧ 平台格式 + 禁用清单 | 平台（决定段长 / 小标题密度）+ 本篇额外禁用词 | 平台对齐 `readability_check.py` 的 `PLATFORM_RULES`；禁用清单在 `anti-ai-slop.md` 通用表之上按本篇再加 |

**⛔ BLOCKING**：先复述锚点四项给用户确认 → 用户确认后，由**用户实际确认的锚点**重推实现四项、连同呈现 → **停下、等用户明确确认或修改**，才能往下写两份产物。这是本管线唯一的核心确认门，落定后后续步骤自动连推。

**创作性字段 ≥3 候选（硬规则）**：⑥ 文风、⑦ 结构没有唯一正解，只有「用户想要哪种感觉」，**必须各给 ≥3 个候选、每个带一句「选它是什么效果」**，让用户拍板。给单一选项等于替用户越界拍板。候选从 `voices/_index.md §2` 自动推荐表、`structures/<结构库目录>/_index.md`（查上面的映射表拼目录）出发。聊天呈现格式示例：

```
文风候选（请挑一个，或告诉我你想要的感觉）：
- 冷峻克制 —— 不动声色，情绪压进动作，读起来被镇住。
- 市井烟火 —— 落到具体的物、价钱、地名，读起来亲切接地气。
- 温润细腻 —— 多感官细节、语气柔和，读起来被打动、被接住。

结构候选：
- 倒叙悬念 —— 先抛结局的碎片，再回头拼因果，全程吊着好奇。
- 五段式 —— 起承转合稳，适合稳扎稳打地铺一个完整弧线。
- 环形结构 —— 结尾回到开头同一场景，意味翻转，余味长。
```

预设都不贴时，主动推荐 `custom`，并用大白话讲清这个 custom 到底什么味道，绝不甩一个光秃秃的 `custom`。

**确认值优先**：用户在确认环节改过的字段，一律照办，**不得「优化」回你的推荐**（用户的确认是意图的最高权威）。唯一要主动处理的例外——**用户改了某个锚点、却没碰依赖它的下游实现字段，导致下游失协调**，则替他把没碰的下游重推到协调，并在 `design_spec.md` 交接说明里讲明调了哪个、为什么调：

| 用户改动的锚点 | 重推（仅用户没碰、被带得失协调的下游字段） |
|---|---|
| ④ 情绪落点 / 核心信息 | 结构候选偏向（如「意难平 → 治愈」时结构从倒叙悬念偏向环形 / 五段式弱反转）、大纲情绪推进 |
| ① 体裁 | 结构库整组换（查映射表）、平台默认、人称适配 |
| ② 题材 / 场景 | 场景手册换、禁用清单与信任状侧重 |
| ③ 目标读者 | 文风口语档位、篇幅、语气 |

一句话：**照办用户每一个显式选择；只在他没表态、又被他的选择带得不协调的地方替他补齐并交代清楚。**

**产物两份**（职责不同，别写串）：
- `<项目>/design_spec.md` —— 设计说明书（给人看）：八项确认的最终值 + 为什么这么定 + 交接说明 + **分节大纲**（每节 800–1200 字，写明「本节任务」+「读完本节读者应有的感受」）。
- `<项目>/spec_lock.md` —— 写作契约（给写手 / 机器看）：**只输出 `##` 段头与 `- key: value` 数据行，绝不把骨架里的 `>` 说明块抄进去**（写手每节机读它、`continuity_check.py` / `readability_check.py` 也机读它，混进散文会干扰机读、稀释约束）。八个固定段名 `update_spec.py` 认死：`体裁` / `目标` / `文风锁定` / `结构` / `人物档案` / `伏笔表` / `禁用清单` / `平台格式`。

**小说专属（体裁 = short-story 时，写手动笔前必须填完两张表）**：
- **人物档案**：每个有名字的人物登记 Core Four（`want` / `need` / `wound` / `lie` + 2–3 句 `语料`），主角能追问「为什么」追到 wound。竖线字段名 `continuity_check.py` 逐字解析，一个字不能改；分隔符 `|` 与字段冒号 `:` 用**半角**。
- **伏笔表**：每条登记 `埋点` / `回收` / `状态`，状态三态 `已规划` / `已埋未收` / `已回收`，脚本只认 `已回收` 为终态。
- 为什么必须开写前填完：`continuity_check.py` 拿这两张表当标准答案扫正文，表空着连贯性检查等于没有标准可依、整条防线失效。

**✅ 检查点**：
```markdown
## ✅ Step 4 · 策划完成
- [x] 八项确认全部有明确值，锚点在前、实现由锚点重推
- [x] 创作性字段（文风 / 结构）各给过 ≥3 候选、每个带效果说明，由用户拍板
- [x] 用户改过的字段原样保留；失协调的下游已重推并在交接说明里交代
- [x] design_spec.md 章节齐全，含分节大纲（每节 800–1200 字 + 本节任务 + 读者应有感受）
- [x] spec_lock.md 只有数据行，段名 / 字段名对得上 update_spec.py 认的那套，没抄说明块
- [x] 小说：人物档案 Core Four 齐全、伏笔表三态填完
- [x] 全程没写过任何一句正文（含示例开头）

```

**每写一节，动笔前把这套固定动作走一遍——不是第一节走一遍就够，是每一节都走**（对应全局纪律 6，抗上下文压缩漂移）：

### Step 7 · 质检

🚧 **GATE**：全部分节初稿完成（`drafts/*.md` 齐全）。

先读岗位说明书：
```
Read references/editor.md
```

**一条铁边界：审校只诊断、产出问题清单，不动手改**（改是润色的活）。三步诊断：

**第一步 · 跑脚本拿客观指标**（按体裁选跑，产物落 `reviews/`）：

```bash
# 所有体裁都跑 —— AI 味五维，总分 < 35 直接打回
$WRITING_PY ${SKILL_DIR}/scripts/ai_slop_checker.py <正文.md> --spec-lock <项目>/spec_lock.md

# 所有体裁都跑 —— 平台合规，以脚本报错为准
$WRITING_PY ${SKILL_DIR}/scripts/readability_check.py <正文.md> --platform <契约里锁的平台> --spec-lock <项目>/spec_lock.md

# 仅小说加跑 —— 伏笔 / 人物 / 人名连贯性，拿契约当标准答案
$WRITING_PY ${SKILL_DIR}/scripts/continuity_check.py <正文.md> --spec-lock <项目>/spec_lock.md
```

阈值：`ai_slop_checker.py` **总分 50、低于 35 打回重写**；`--spec-lock` 是为了把契约里本篇额外禁用词一并纳入检测。`--platform` 取契约锁的平台（`公众号` / `朋友圈` / `小红书` / `知乎` / `通用`），别套错。

**第二步 · 按体裁跑人工诊断**（脚本查不出的文学判断，纯靠人）：

| 体裁 | 人工诊断法 | 出处 |
|---|---|---|
| 微信文案 | AI 痕迹仪表盘 + 转化要素缺失自检（目标动作可否观测、是不是单一卖点、结尾是不是具体动作、证据是不是形容词充数） | `genres/wechat/core.md` |
| 短篇小说 | 逐场景过 GCOS（Goal-Conflict-Outcome-Sequel 四格量每个场景，填不出 Goal/Conflict、Outcome 含糊的标「软场景」） | `genres/story/core.md` |
| 文章 | 七轮扫描（每轮只盯一个维度：清晰度 / 语气一致 / 「所以呢」/ 举证 / 具体化 / 情绪浓度 / 消除犹豫点） | `genres/article/core.md` |

**第三步 · 合并三级清单**：脚本命中 + 人工诊断合并成一张 🔴（必须改）/ 🟡（应该改）/ 🟢（可以改）清单，**每条带行号 + 一句「为什么要改」，不写改法**（改法是润色的事）。

**读者评分团 —— 放行的最终关卡**：设 **3–5 个不同身份**（目标读者 / 怀疑论者 / 编辑 / 观点型文章加反方代表 / 说明型 · 小说加新手读者），各站自己立场给 1–10 分，取均分。**均分 ≥8 才放行**。5–6 分需重写重灾段落，3–4 分回策划重新定型，1–2 分推翻重来。

**退回润色最多两轮**：均分 <8 就把清单退给润色（Step 8）改，改完回来重新评分。**最多两轮**。两轮仍不过关，**不许无限循环、也不许糊弄放行**——如实把「两轮改后仍 X 分、卡在哪」报告用户，交还用户决定（接受 / 大改 / 推翻）。理由：无限循环是浪费用户时间成本却假装推进，糊弄放行是拿次品交差；碰到过不去的坎，诚实上报比假装解决更负责。

**✅ 检查点**：
```markdown

```
