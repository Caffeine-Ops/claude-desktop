# 日常翻译（Translate）

用户给一段文字、一封邮件或一份文件，想要另一种语言的版本时用这个技能。
翻译本身不需要任何脚本——你自己就是翻译引擎。这份手册管的是**质量纪律**：
什么要保留、什么不许猜、长文件怎么不翻着翻着就变味。

## 先弄清三件事（一句话确认，别开长问卷）

1. **目标语言**：用户没说就按「中文 ⇄ 英文」的方向推断（原文是中文就译英文，反之译中文）。
   其他语言必须用户明说。
2. **用途 / 场合**：商务邮件、学术论文、产品文案、日常聊天……决定语气和用词档位。
   用户没说就按原文的语气走，不要擅自升格成「正式」。
3. **输出形态**：纯译文（默认）、双语对照、还是落成文件。用户给了文件默认落文件。

三件里能从原文和上下文推断出来的就不要问；只问真拿不准、且答错会返工的那一件。

## 铁律

### 一、意思准确优先于文采

- 不增不减：原文没有的信息不加，原文有的信息不丢。「润色」也只改表达不改事实。
- 数字、日期、金额、单位、人名、公司名、产品名、链接、代码：**原样照搬**，
  日期格式按目标语言习惯调整（如 2026年9月14日 ⇄ September 14, 2026）。
- 拿不准的词**不硬猜**：保留原文并用「〔原文：xxx〕」标出，文末列「待确认」清单。
  译错一个专业术语比留一个标记的代价高得多。

### 二、结构原样保留

标题层级、段落切分、列表、表格、加粗、代码块、引用——译文和原文一一对应。
用户拿到译文应该能和原文逐段对上。Markdown 语法照抄，只翻里面的文字。

### 三、术语前后一致

同一个术语在整份材料里只能有一种译法。长文件开工前先扫一遍挑出术语，
在心里（或明写）定一张表再翻；用户给了术语表就**无条件按表来**，哪怕你觉得
表上的译法不是最优的——一致性归用户管，你只负责提醒一句。

### 四、地道，但不过头

- 目标语言的读者读起来应该像母语写的：语序、搭配、习语按目标语言习惯来，
  不要逐字对译（中式英语 / 翻译腔都算失败）。
- 但**语气档位跟原文走**：原文随意就译得随意，原文正式就译得正式。
  「润色」是用户明确要求时才做，且要说明改了哪类表达。
- 邮件：称呼、客气程度、结尾套话按目标语言的惯例换，不要直译「此致敬礼」。

## 各类任务怎么做

### 一段文字 / 一封邮件

直接输出译文，不要在前面加「好的，以下是翻译」之类的废话。译文后如有
「待确认」项再附一小节。用户要双语对照时按**段落**做「原文在上、译文在下」，
不要按句拆——句级对照打断阅读，段级才方便核对。

### 整份文件（txt / md / docx / pdf）

1. **取料**：`.txt` / `.md` 直接读。`.docx` / `.pdf` 借用同一插件下的文档处理技能取文字
   （它已处理好编码、扫描件识别等坑，不要自己现写解析代码）：

   ```bash
   # macOS / Linux —— 必须用 source，脚本要把 $DOC_CONVERT_PY 导回你的 shell
   source ${SKILL_DIR}/../doc-convert/bin/ensure-python.sh
   "$DOC_CONVERT_PY" ${SKILL_DIR}/../doc-convert/scripts/doc_text.py 原文.pdf --outdir 取料/
   ```

   > Windows 改跑 `${SKILL_DIR}\..\doc-convert\bin\ensure-python.cmd`，末行打印 `DOC_CONVERT_PY=<path>`。
   > 首次运行要下载依赖（几分钟），**开始前告诉用户这次要等**。

   stdout 的体检报告里 `scanned: true` 表示扫描件没有文字层——如实告诉用户，
   让他先用文档处理技能做文字提取，或换一份有文字层的文件；不要拿渲染图硬认。

2. **分块翻**：`chars > 6000` 就按段落边界切块（每块约 3000 字），**先定术语表再翻第一块**，
   每翻完一块回看术语表，防止后面块的译法漂移。块之间不要打断段落。

3. **落盘**：默认输出与原文同格式的 Markdown（`原文名.译文.md`）到会话工作目录；
   用户要 Word 时把 Markdown 交给文档处理技能的 `md_to_docx.py`：

   ```bash
   "$DOC_CONVERT_PY" ${SKILL_DIR}/../doc-convert/scripts/md_to_docx.py 原文.译文.md -o 原文.译文.docx
   ```

   注意它的 Markdown 子集限制（不支持引用块 / 图片 / 链接语法，表格每行要以 `|` 开头），
   落盘前把译文改写成受支持的形式。skill 目录在打包后是**只读**的，产物一律写到会话工作目录。

4. **交付时说清覆盖范围**：翻了几段/几页、哪些地方留了「待确认」标记、术语表放在哪。
   没翻完的部分明说，不要假装全文翻完了。

### 中译英润色

先直译出准确版本，再按用户给的场合改成地道表达；交付时**只给最终版**，
但在末尾用两三条点出你改动的表达类型（如「把三个并列短句合成一个复合句」
「替换了两处中式搭配」），让用户知道哪里被润过、能自己判断要不要保留。

### 整理术语表

输出三列：**术语 · 译法 · 出现语境（原文短句）**。只收专业术语、固定说法、
反复出现的机构/产品名；日常词不收。给出的译法要能直接用在后续翻译里，
拿不准的在译法列标「？」并说明候选，让用户拍板。

## 不做的事

- 不改原文的事实、立场和信息量；发现原文有错只在「待确认」里提醒，译文照原文翻。
- 不替用户决定目标语言的地区变体（美式/英式、简体/繁体）——原文或用户没提示就用
  美式英语 / 简体中文，并在需要时提一句可切换。
- 不对整份文件只翻一半就交付；量大就分块，分块也要翻完。
