# 文档处理技能 PR 2 设计方案 —— A 类「需要理解内容」的 4 条能力

> 承接 `2026-08-10-doc-convert-skill-design.md`（下称「总设计」）的交付顺序第 2 步。
> PR 1（B 类 4 条纯脚本转换）见 PR #30，**本 PR 依赖 #30，从 `feat/doc-convert-skill` 开出**。
> 2026-08-11 定稿。

## 本 PR 的范围

总设计「功能清单」里的 A 类 4 条：

| 话术标签 | 用途 | 文件槽 |
|---|---|---|
| 图片提取文字 | 照片/截图/扫描件 → 可编辑文本，可输出 Word / Markdown | 【图片文件】 |
| PDF 表格转 Excel | 财报/对账单/报价单里的表格 → 能算的 Excel | 【PDF 文件】 |
| 票据批量转台账 | 一批发票/收据照片 → 结构化 Excel | 【票据图片】 |
| 长文档提炼 | 几十页文档 → 摘要 / 大纲 / Markdown | 【文稿文件】 |

与 PR 1 的本质区别：**PR 1 走脚本，PR 2 走模型**。纯格式转换是确定性任务，
用大模型是杀鸡用牛刀；「必须看懂内容才能转对」这四条才是 AI 打得过传统工具的地方
（判断依据见总设计「核心产品判断」）。

## 六个已拍板的决策

| # | 决策点 | 选定 | 被排除的选项与理由 |
|---|---|---|---|
| 1 | 脚本与模型的分工 | **三段式：取料（脚本）→ 看懂（模型只出 JSON）→ 装配（脚本）**，模型永远不直接生成 xlsx/docx | 「模型直接写文件」→ 它会现场编 Python，每次编得不一样，正是总设计决策 #3 排除「零技能」方案的同一理由；且无处安放确定性质检 |
| 2 | 模型拿不准时 | **一律留空 + 标「无法识别」+ 结尾附核对清单，绝不猜** | 「尽力猜 + 标注把握程度」→ 用户十有八九忽略标注直接用，这正是 PR 1 极力避免的「看起来正常实则有缺陷」；「分场景，钱和数字严格、文字宽松」→ 规则复杂，且「错了一眼能看出来」这个前提在长文档摘要里并不成立 |
| 3 | 票据台账的表头 | **内置默认列 + 识别 1–2 张样本后让用户确认一次再批量** | 「固定一套列不商量」→ 火车票车次、酒店入住天数这类特有信息全丢；「模型看整批自己定」→ 两次跑同一批票列可能不一样，且要把图看两遍，慢一倍贵一倍 |
| 4 | PDF 表格转 Excel 的路线 | **有文字层：脚本抽 + 模型对着原页渲染图校对结构；无文字层：模型看图读，全套严格标记** | 「一律模型看图」→ 本来 100% 准确的数字交给模型去看，财报错一位小数点就是事故；「只做有文字层的，扫描件直接拒绝」→ 对账单/报价单里扫描件占比不低，用户会觉得这条能力成天拒绝他 |
| 5 | 长文档提炼的产出 | **摘要 / 大纲 / 全文 Markdown 三档，开工前问用户要哪一档** | 「默认摘要+大纲一起给」→ 用户想要的若是全文转写就白跑一轮；「砍掉全文转写」→ 话术写的是「→ 摘要/大纲/Markdown」，砍了得改话术，且「PDF 变成我能编辑的 Markdown」是真实高频需求 |
| 6 | 批量任务的规模 | **边跑边落盘（JSONL 追加，可断点续跑）+ 超阈值先告知预计耗时** | 「设硬上限超了拒绝」→ 分批的活推给用户干，且分批后几张表还得他自己拼；「不管，一把梭」→ 中断即全白跑，用户也不知道要等多久，容易以为卡死去关窗口 |

## 核心架构：三段式流水线

```
① 取料（脚本）        →  ② 看懂（模型）      →  ③ 装配（脚本）
   文件 → 模型能读的东西     只输出 JSON            JSON → .xlsx/.docx/.md
   文字 / 表格候选 / 页面 PNG
```

**这条边界一次解决三个问题**，是本 PR 的地基：

1. **质量可控**。装配交给固定脚本，输出稳定；模型现写 Python 的不确定性被挡在门外。
2. **反幻觉能落地**。装配脚本可做确定性检查（金额列出现非数字、必填全空、行列不齐、
   存疑占比过半）→ **直接拒绝出文件**。这是 PR 1「宁可不产出，也不产出一份看起来
   正常实则有缺陷的文件」在模型侧的落法。
3. **断点续跑白送**。JSON/JSONL 本身就是中间存档，识别一条追加一条，
   中断重跑只补缺的，不用另设机制。

**代价**：多一层中间格式，SKILL.md 要把每条能力的 JSON 形状写清楚。这是提示词工程的
常规成本。

例外：**「图片提取文字」不走 JSON 中间层**——它的产物 Markdown 本身就是最终形态，
②③ 合并。为一致性硬套 JSON 只会平添一次无意义的转换。

## 反幻觉规范（四条能力共用）

### 模型侧的约定：值和把握分开写

```json
{ "日期": "2026-03-01", "金额": null, "开票方": "某某科技有限公司",
  "_存疑": [{ "字段": "金额", "原因": "折痕遮挡，只能看到 1?8.50" }],
  "_来源": "IMG_0012.jpg" }
```

- 拿不准的字段**留空**，另在 `_存疑` 里写清字段名和原因。
- **`null` 且不在 `_存疑` 里 = 票据上本来就没这项**，与「看不清」严格区分。
  这个区分是刚需：把「本来就没有」也标成「无法识别」会制造大量假警报，
  用户很快就会无视所有黄色单元格，标记随之失效。
- 数值型字段用 JSON number 类型输出（`128.5` 而非 `"128.5"`）。
  「这是不是一个数」的判断由模型给出，装配脚本据此决定写数值还是写文本——
  写成数值的单元格才能直接参与 Excel 求和。

### 用户侧看到的东西

| 产物 | 无法识别处怎么呈现 |
|---|---|
| **Excel** | 单元格填 `⚠ 无法识别` 并**染黄底**；末尾追加一张「待核对」工作表：来源 / 页码 / 字段 / 原因 |
| **Markdown / Word** | 正文用 `【无法识别】` 占位；文末附「待核对」小节，标明每处位置 |

染黄底不是装饰：用户拿到 Excel 是拖着滚动条扫的，不会逐格看，
**颜色是唯一能在扫视中被捕捉到的信号**。

### 装配脚本的硬拒绝清单

延续 PR 1 那张「脚本会拒绝干活的几种情况」表的风格，报错格式同样是
`[doc-convert] 错误：<中文说明>` 走 stderr + 非零退出码 + 告诉用户下一步干什么，
不漏 Python 堆栈。

| 情况 | 脚本反应 |
|---|---|
| 一行数据都没有 | 拒绝出 Excel |
| 表头为空 | 拒绝 |
| 某行出现表头里没有的字段 | 拒绝并列出是第几行、多了哪个字段（防止模型偷偷加列）。字段缺失视为空值，允许 |
| **存疑单元格占比 > 50%**（分母 = 行数 × 列数） | **拒绝出文件**，告知这批图质量太差，建议重拍或改用扫描件 |
| PDF 有密码保护 / 页码越界 | 沿用 PR 1 已有的措辞 |

50% 阈值的立场：一份一半是问号的台账，用户核对的工夫比自己录还多，不如不给。
阈值可用 `--max-uncertain-ratio` 覆盖，但默认值就是硬门禁。

## 四条能力详设

### 1. 图片提取文字

```
img_prep.py 规格化 → 模型看图 → Markdown → （要 Word 时）md_to_docx.py
```

- 输出 **Markdown，还原图上肉眼可见的结构**（标题、列表、简单表格）。
  纪律写进 SKILL.md：**不新增层级、不改写措辞、不补全句子**——
  版面还原和内容创作只隔一层窗户纸，越界就成了另一种幻觉。
- 要 Word 时把这份 Markdown 丢给 PR 1 已有的 `md_to_docx.py`，**不新增脚本**。
- 拒绝条件：整张图认不出任何文字 / 根本不是文字图片 → 不产出文件，直说。

### 2. PDF 表格转 Excel

| 步 | 谁 | 干什么 |
|---|---|---|
| 取料 | `pdf_tables.py` | 先体检有无文字层；有则按坐标与框线抽表存 JSON，无则标记 `scanned: true` |
| 取料 | `pdf_render.py` | 把相关页渲染成 PNG |
| 看懂 | 模型 | 对照 PNG 核对 JSON |
| 装配 | `rows_to_xlsx.py` | 出 Excel + 待核对表 |

**核心纪律：模型只准改结构，不准改数字。** 脚本抽出来的数字是从文件里按坐标读的，
准确率 100%（事实核查 #3）；模型是看图认字，会看错小数点。所以模型只负责它擅长的：
合并跨页表头、把挤在一起的两张表拆开、剔除混进表里的页眉页脚行。
**模型若认为某个数字抽错了，不许自己改，只能记进「待核对」清单交给人看。**

扫描件分支：没有文字层可抽，只能模型看图读数，此时全套严格标记生效，
且**必须在交付时显眼告知「这份是扫描件，数字是认出来的不是读出来的，请核对」**。

拒绝条件：不是扫描件却一张表都没找到 → 不出空 Excel，直说「这份 PDF 里没找到表格」。

### 3. 票据批量转台账

```
img_prep.py 规格化 → 识别 1–2 张样本 → 提议列给用户确认
  → 逐张识别，每张立刻追加一行到 ledger.jsonl
  → rows_to_xlsx.py 出 Excel
```

- 默认列：**日期 / 票据类型 / 开票方 / 金额 / 税额 / 发票号 / 摘要 / 来源文件**。
  最后一列是刚需——用户核对时必须知道这行来自哪张图。
- 中间文件用 **JSONL**（一行一条 JSON，天生适合追加）。中断重跑只补没做完的。
- 超过 **20 张**先告知预计耗时再开工。
- 某张图根本不是票据：那一行标注清楚，**不中断整批**；全部失败才不出文件。
- 装配脚本与能力 2 **共用** `rows_to_xlsx.py`。

### 4. 长文档提炼

| 步 | 谁 | 干什么 |
|---|---|---|
| 取料 | `doc_text.py` | PDF/Word/txt/md → 带页码锚点的纯文本 + 体检报告（页数、字数、每页字数、是否扫描件） |
| 分流 | — | 扫描件 → 告知用户这份没有文字层，建议走「图片提取文字」；超阈值 → 分块 |
| 看懂 | 模型 | 按用户选的档位产出（摘要 / 大纲 / 全文 Markdown） |
| 装配 | — | 直接写 `.md`；要 Word 走 `md_to_docx.py` |

**最大的风险不是总结得不好，是模型只读了前面一小截就开始总结，而且它不会告诉你。**
两条硬规矩写进 SKILL.md：

1. 全文超过 **30000 字**必须**分块逐块读、每块出小结、最后合并**
   （每块约 8000 字，块间重叠约 200 字防切断句子）。
2. 产出开头必须写明覆盖范围（「本摘要基于第 1–58 页全文」）。
   摘要里的关键数字与结论要带页码出处，**原文没有的数字一个都不许出现**。

超过 **60 页**先告知预计耗时。

## 新增脚本（5 个）

每个只干一件事，都能单独测试。

| 脚本 | 命令行 | 输出 | 主要拒绝条件 |
|---|---|---|---|
| `img_prep.py` | `<img...> -d OUTDIR [--max-edge 1600]` | 规格化后的 JPG + 一份「原名 → 新名」清单 JSON | 不是图片；HEIC 且本机既无 pillow-heif 又无 sips |
| `doc_text.py` | `<file> [--outdir DIR]` | `<stem>.text.txt`（带 `[P3]` 页锚点）+ stdout 体检 JSON | 文件损坏、连页数都读不出；`.doc` 旧格式（提示另存为） |
| `pdf_render.py` | `<pdf> --pages "1-3,7" -d OUTDIR [--scale 2]` | `page-0001.png` … | 加密 PDF；页码越界（报总页数） |
| `pdf_tables.py` | `<pdf> [--pages ...] -o tables.json` | 见下方 JSON 形状 | 加密 PDF；非扫描件却零表格 |
| `rows_to_xlsx.py` | `<rows.json\|.jsonl> -o out.xlsx [--headers ...] [--sheet 名]` | Excel（含待核对工作表） | 见上方硬拒绝清单 |

关键取值及其理由：

- **`--max-edge` 默认 1600**：模型看图前会把长边压到约 1568 px，再大只多花钱不多认字。
- **`--scale` 默认 2**：A4 @2 倍约 1191×1684，与上面那条对齐，实测出图 37 KB。
  认不清时可对单页提高 scale 重渲染局部。
- **扫描件判定：PDF 平均每页可提取字符 < 50**。按页给出明细，
  混合型文档（部分页是扫描）标出具体是哪几页，不是一刀切。
- **JSONL 模式必须显式传 `--headers`**：各行字段可能不齐，靠首行推断会静默漏列。

`pdf_tables.py` 的 JSON 形状：

```json
{ "source": "报价单.pdf", "total_pages": 12, "scanned": false,
  "tables": [ { "table_id": 1, "page": 3, "n_rows": 8, "n_cols": 5,
                "rows": [["项目","单价","数量","金额","备注"], ...] } ] }
```

`rows_to_xlsx.py` 的输入形状：

```json
{ "headers": ["日期","票据类型","金额","来源文件"],
  "meta": { "标题": "2026年3月报销台账" },
  "rows": [ { "日期": "2026-03-01", "金额": 128.5, "_存疑": [...], "_来源": "IMG_0012.jpg" } ] }
```

## 依赖与体积

```
pdfplumber>=0.11                              # PDF 抽文字/抽表格 + 自带 pypdfium2 渲染
pillow-heif>=0.16; sys_platform == "win32"    # 仅 Windows：HEIC 解码
```

`pillow-heif` 用 pip 的**平台条件依赖**只在 Windows 安装：macOS 走系统自带 `sips`
（事实核查 #5），不让 mac 用户为 Windows 的坑多付 12 MB。
Linux 两者皆无时明确报错让用户自行转格式，不硬撑。

| | PR 1 后 | PR 2 后 | 增量 |
|---|---|---|---|
| macOS venv | 66 MB | **约 99 MB** | +33 MB |
| Windows venv | 66 MB | **约 111 MB** | +45 MB |
| 安装包 | 不变 | 不变 | 脚本是纯文本 |

**仍然刻意不装 pandas**（理由同总设计：它加 numpy 约 84 MB，比其余所有库加起来还大）。
表格数据在本 PR 里始终是 Python 原生的 list of list，openpyxl 直接写，用不上 DataFrame。

## 测试策略

| 层 | 覆盖 |
|---|---|
| **pytest** | 5 个脚本各自的确定性行为：抽表结果、页码越界报错、扫描件判定、HEIC 分支、`rows_to_xlsx` 的五条拒绝规则与黄底染色。样本 PDF 用 reportlab 现造，不往仓库塞大文件 |
| **bun test + typecheck** | 话术条数 8、三个新槽的格式映射、chip 注册无遗漏 |
| **人工验收** | 模型侧无法自动测。`tests/fixtures/` 放几份**自造的、答案已知**的样本（假发票、带表格的 PDF、模拟扫描效果的图），配一张「验收清单」：每条能力该出什么、错成什么样算不合格。照单对答案，**不靠模型自评**（同 writing 技能用脚本量化的传统） |

「先有答案、再有产出」是这套人工验收的关键：事后拿模型的产出当标准答案，
等于自己给自己打分。

## 已知限制

- **模型侧质量不可自动回归**。改提示词只能靠人工跑验收清单，成本高、频率低。
  真正的自动化 evals 不在本 PR 范围。
- **扫描件的数字终究是认出来的**。已用严格标记 + 显眼告知把风险交回用户，
  但做不到「保证正确」。财务用途请以原件为准这句话要在交付时说出口。
- **表格结构复杂时仍会散架**。跨页跨栏、嵌套表头、无框线三者叠加的表，
  脚本抽 + 模型校对也不保证还原，此时按纪律记进「待核对」而不是硬凑。
- **venv 涨到约 100 MB**。这是第 5 份重复 venv（总设计事实核查 #11），
  合并 venv 的触发信号仍是「用户开始反馈这软件占我十几个 G」。

## 本轮不做

| 不做的事 | 理由 |
|---|---|
| 自动化 evals 打分脚本 | 需要一批标注样本和评分标准，工作量单独成篇；本轮先用人工清单顶 |
| PDF → Word 高保真版式还原 | 同总设计：呼声最高但最易翻车 |
| 手写体识别 | 印刷体已能覆盖发票/报表主力场景，手写准确率低到会拖垮整条能力的口碑 |
| 表格跨页自动合并成一张 | 判定「这两页是同一张表」本身就不可靠，交给用户在待核对清单里确认 |
| 合并 5 个技能的 venv | 同总设计决策 #5 |
