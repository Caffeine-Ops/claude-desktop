# Writing 已有作品优化设计

日期：2026-07-28  
状态：已定稿（§14 三项决策已拍板，2026-07-28）

## 1. 背景

Writing 当前覆盖从零写作、粘贴文字改写、只润色、文风学习等能力，但缺少一条面向
“用户已经有完整作品”的清晰产品入口。现有“改写这段文字”要求用户手动粘贴原文，
不适合较长文章、完整小说和 Word/PDF 文稿，也没有在修改前明确“改到什么程度”。

“优化已有作品”存在天然歧义：它可能只表示纠错润色，也可能允许调整段落、结构乃至
重新创作。如果 AI 直接按自己的理解动稿，最严重的失败不是文字质量差，而是用户的
个人表达、结构选择或原意被擅自覆盖。

本设计复用“制作 PPT → 用我的 PPT 模版”的文件槽交互，让用户从 Writing 推荐场景
上传自己的作品；上传后先诊断、再确认修改强度，最后路由到已有的 `polish-only` 或
`rewrite` 工作流。

## 2. 目标

1. 用户可以通过 Writing 推荐场景直接上传完整作品，不必复制粘贴长文。
2. AI 在修改前先给出基于原稿的作品体检，不提前输出改写正文。
3. 用户能够明确选择轻度润色、标准优化或深度改写，并知道每档允许改什么。
4. 明确意图的用户可以走润色或深度改写快捷入口，减少不必要的往返。
5. 所有改动可与原稿对账，且原稿始终保留，不被覆盖。

## 3. 非目标

- 不新增独立上传页、向导页或原生确认页；一期复用聊天推荐 prompt 和文件占位 pill。
- 不在客户端解析或评价文稿内容；文件转换、诊断和分流由 Writing skill 完成。
- 不覆盖长篇小说、超长连载的跨会话整体重构。
- 不做多人批注、修订模式或 Word Track Changes。
- 不把“优化”自动等同于“全部重写”。

## 4. 产品方案

采用“一主两捷径”的信息架构。

> **一期落地范围（§14 决策 1，2026-07-28 拍板）**：推荐区一期**只展示主入口
> `优化已有作品`**，§4.2「润色已有作品」与 §4.3「深度改写作品」两个快捷入口的
> 推荐 chip **推迟到二期**。原因：主入口本身在确认硬门里就覆盖了轻度润色 / 标准
> 优化 / 深度改写三档意图，先保证推荐区不拥挤，两个快捷 chip 待主入口点击率与
> 三档选择分布的数据出来后再决定是否补。**注意**：`optimize-existing.md` 内部
> **仍然完整实现三档分流**（用户在确认硬门里选档），只是不在推荐区额外摆两个
> chip——§4.2/§4.3 描述的档位语义与路由规则一期就要建好，改变的只是「有没有对应
> 的独立推荐 chip」。

### 4.1 主入口：优化已有作品

推荐场景名称：`优化已有作品`

预填 prompt：

```text
帮我优化【文稿文件】。请先检查内容、结构、表达、文风和 AI 痕迹，告诉我主要问题，
并推荐轻度润色、标准优化或深度改写。在我确认修改强度前，不要改正文。
```

适用于用户只知道“想优化”，但还不确定应该小修还是大改的场景。

### 4.2 快捷入口：润色已有作品

推荐场景名称：`润色已有作品`

预填 prompt：

```text
帮我润色【文稿文件】。先诊断语言、节奏和 AI 痕迹，再在不改变原意、事实、结构和
个人表达的前提下修改；如发现需要调整观点或结构的问题，只标出来，不要擅自处理。
```

该入口等同于用户提前选择“轻度润色”。AI 可以在范围内完成诊断后直接修改，不再询问
修改强度；发现超出边界的问题时单独提示。

### 4.3 快捷入口：深度改写作品

推荐场景名称：`深度改写作品`

预填 prompt：

```text
帮我深度改写【文稿文件】，目标是【说明用途或期望效果】，必须保留【说明不能改的
内容】。请先给出诊断和改写范围，等我确认后再改正文。
```

该入口等同于用户提前选择“深度改写”，但由于结构、文风和内容取舍都会发生变化，
仍保留一次硬确认。

### 4.4 与现有“改写这段文字”的关系

- 保留 `改写这段文字`，服务短文本和直接粘贴场景。
- 新增三个入口服务完整文件，不替换短文本入口。
- 三个文件入口必须使用 `【文稿文件】`，以触发可点击文件占位 pill。

## 5. 文件交互

### 5.1 复用现有文件槽

沿用 `filePlaceholderPlugin`：推荐 prompt 中以“文件”结尾的 `【文稿文件】` 被渲染为
可点击 pill；用户选择文件后，占位原位替换为文件 mention。用户也可以直接拖入文件。

不为 Writing 新建上传组件。

### 5.2 支持格式

一期支持 Writing 的 `source_to_md.py` 已能处理的格式：

- `.txt`
- `.md`、`.markdown`
- `.docx`
- `.pdf`

不宣称支持 `.doc`。当前转换脚本不支持旧版 Word 格式，应在选择器中置灰，而不是允许
选择后再报错。

在 `acceptForPlaceholder()` 中为“文稿/作品/稿件”增加组合映射：

```text
.txt,.md,.markdown,.docx,.pdf
```

该映射应放在单一格式关键词之前，避免“文稿文件”落入无过滤状态。文件选择器过滤只作
引导，skill 仍需对实际后缀做校验并给出可理解的错误信息。

### 5.3 原稿保护

- 文件先转换并保存到项目的 `sources/`，作为不可覆盖的原稿。
- 诊断报告保存到 `reviews/`。
- 修改后的版本保存到 `output/`。
- 不原地修改用户上传的文件。

## 6. 主入口流程

```text
选择“优化已有作品”
  → 上传文稿
  → 转换为 Markdown 并保留原稿
  → 识别体裁、平台和作品完整度
  → 作品体检
  → 推荐修改强度
  → 用户确认（硬门）
  → 路由到对应工作流
  → 修改、复检、输出对照
```

### 6.1 作品体检

体检只诊断，不修改正文。输出必须简短、可决策，不把脚本原始日志直接倾倒给用户。

固定检查五个维度：

| 维度 | 要回答的问题 |
|---|---|
| 内容 | 核心信息是否清楚，有无重复、缺口或事实风险 |
| 结构 | 顺序是否合理，段落或场景是否承担明确任务 |
| 表达 | 是否啰嗦、含混、书面腔过重或节奏单一 |
| 文风 | 语气、人称和个人表达是否一致 |
| AI 痕迹 | 套话、AI 句式、均匀结构和抽象表达是否集中 |

体检结果按 `必须处理 / 建议处理 / 可选处理` 分级，每条说明“为什么”，但不提前给完整
改写句。最后必须给出一个推荐档位及理由。

### 6.2 三档修改强度

| 档位 | 允许改动 | 不允许改动 | 路由 |
|---|---|---|---|
| 轻度润色 | 错字、标点、语病、用词、句子节奏、AI 痕迹 | 观点、事实、段落顺序、结构 | `polish-only.md` |
| 标准优化 | 轻度润色全部能力；删减重复；局部改写；必要时拆合段落 | 核心观点、关键事实、整体结构、人物与情节走向 | `rewrite.md` 定向路径 |
| 深度改写 | 重排结构、重写段落、调整叙事顺序和文风；按目标平台重构 | 用户明确列入“必须保留”的内容 | `rewrite.md` 全量路径 |

“标准优化”必须作为默认推荐的中间档，但 AI 应根据体检结果推荐，而不是机械默认。若原稿
已经成熟，只推荐轻度润色；若结构性问题决定成败，则推荐深度改写。

### 6.3 确认硬门

主入口在体检后必须停止，等待用户明确选择档位或调整范围。确认信息至少包括：

- 选择的修改强度；
- 必须保留的内容；
- 目标用途或平台（仅在会影响修改标准时询问）；
- 是否处理“可选”问题。

用户未确认前，不生成优化后的正文，不创建假定的改写方案，也不把示例句伪装成定稿。

## 7. Skill 工作流改造

### 7.1 新增统一入口工作流

新增 `skills/writing/workflows/optimize-existing.md`，只承担：

1. 接收文件并保存原稿；
2. 做五维体检；
3. 推荐三档强度；
4. 等待确认；
5. 把确认结果路由到已有工作流。

主 `SKILL.md` 的独立工作流索引增加该文件，并在 frontmatter description 中补充“上传
已有作品优化、作品体检”等触发语。详细诊断与分流规则放在新工作流，不继续扩张已接近
500 行的主文件。

### 7.2 调整现有工作流边界

- `polish-only.md` 保持“不动结构、不动观点、只动文字”，作为轻度润色唯一执行源。
- `rewrite.md` 明确接收来自 `optimize-existing.md` 的已确认档位；已有的 Step 0 自动判别
  只用于用户绕过新入口、直接在对话中提出改写要求的场景。
- 标准优化进入 `rewrite.md` 时，将“整体结构不可改”写入本次修改约束。
- 深度改写进入 `rewrite.md` 时，将“必须保留项”写入本次修改约束，并维持原有硬确认。
- 不复制两份工作流的执行规则到 `optimize-existing.md`，避免后续口径漂移。

### 7.3 角色边界

- 体检阶段使用审校角色：只诊断，不动手。
- 执行阶段按路由进入润色/改写角色。
- 修改后重新进入审校角色复检。
- 禁止审校在体检阶段夹带“顺手改好”的正文。

## 8. 输出与对账

每次交付至少包含：

1. 优化后的完整作品文件；
2. 修改摘要；
3. 精简改动对照；
4. 未处理但值得注意的问题；
5. 原稿与成稿的完整文件路径。

对照粒度随档位变化：

- 轻度润色：列代表性句级改动，不要求穷举每个标点。
- 标准优化：逐项对应体检中的“必须处理/建议处理”。
- 深度改写：按章节或结构块说明“原稿 → 新稿”的变化及保留项落实情况。

## 9. 错误处理

- 未上传文件就发送：AI 提醒补充文稿，不开始空泛体检。
- 格式不支持：明确列出支持格式，原文件不做任何改动。
- 文件无法提取文字：报告失败原因，建议改传 `.docx`、`.pdf`、`.md` 或 `.txt`。
- 扫描版 PDF 无可提取文字：一期明确提示需要 OCR 或可复制文本，不伪装成已读完。
- 体裁无法判断：只询问会改变诊断标准的一个关键问题，不启动完整八项策划。
- 用户在体检后改变目标：以最新确认值为准，重新计算受影响的修改范围。
- 用户要求直接改：若已明确可验收方向，可进入对应快捷路径；若仍是笼统“优化”，不得
  跳过强度确认。

## 10. 埋点与成功指标

一期建议记录匿名产品事件，不记录文稿正文：

- 三个场景入口的点击率；
- 文件槽点击后成功选中文件的比例；
- 主入口三档强度的选择分布；
- 体检后退出率；
- 用户改选 AI 推荐档位的比例；
- 交付后继续要求“改轻一点/改重一点”的比例。

核心成功信号：用户完成一次修改后，很少再反馈“改得太多”“没按我的意思”或“只是换了
几个词”。

## 12. 验收标准

### 自动化测试

1. `【文稿文件】` 被识别为文件槽，点击后 accept 为
   `.txt,.md,.markdown,.docx,.pdf`。
2. PPT、Excel、图片等现有文件槽映射不回归。
3. 三个 Writing 推荐 prompt 均包含正确文件槽，且主入口明确写出“确认前不要改正文”。
4. Writing skill 校验通过，主索引能够定位 `optimize-existing.md`。
5. 路由测试覆盖轻度润色、标准优化、深度改写三种确认结果。

### 手动走查

1. 上传 `.docx` 文章，经主入口先看到五维体检，确认前没有改写正文。
2. 选择轻度润色后，结构、观点和事实保持不变，输出有代表性对照。
3. 选择标准优化后，只发生局部段落调整，整体结构保持不变。
4. 选择深度改写后，AI 先确认目标与必须保留项，再重构正文。
5. 从“润色已有作品”进入时不重复询问强度；发现结构问题只提示、不擅自修改。
6. 从“深度改写作品”进入时仍有范围硬门。
7. 上传不支持格式或扫描 PDF 时得到明确、诚实的错误信息。

## 13. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 三个入口让推荐区变拥挤 | 主入口优先展示；快捷入口排在现有“改写这段文字”附近，后续依据点击率精简 |
| “标准优化”和“深度改写”边界再次模糊 | 用“整体结构能否改”作为唯一硬边界，并写入路由约束 |
| AI 体检过长，用户还没开始改就流失 | 固定五维、每维只报最高价值问题，完整报告落文件而非全部堆在聊天中 |
| 诊断后 AI 忘记等待确认 | 在 `optimize-existing.md` 设置 BLOCKING 硬门，并加入前向测试 |
| 用户个人文风被去 AI 味规则误伤 | 将“个人表达”列为默认保留项；文风异常只报告证据，不以统一腔调覆盖 |
| 主工作流与两个旧工作流规则重复漂移 | 新工作流只做诊断和路由，执行纪律继续由 `polish-only.md`、`rewrite.md` 单独负责 |

## 14. 决策记录（2026-07-28 已拍板）

1. **推荐区一期只展示主入口** `优化已有作品`；两个快捷入口（润色 / 深改）推迟到
   二期（见 §4 一期落地范围提示、§11 一期/二期）。`optimize-existing.md` 内部三档
   分流照建不误。
2. **“个人表达”默认作为所有档位的必须保留项**——三档都把“用户自己的语气 / 口头禅 /
   用词习惯”列为默认不动项；去 AI 味只报证据，不以统一腔调覆盖用户原声。写进
   `optimize-existing.md` 的档位表与路由约束。
3. **“标准优化”允许拆分 / 合并段落，但禁止改变整体结构**——硬边界统一为“整体结构
   （章节顺序、论证骨架）能否改”。写进 §6.2 档位表与 `rewrite.md` 的标准档约束。
