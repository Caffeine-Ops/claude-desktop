# 写作工作区：覆盖面补齐 + 纸面手动编辑 设计方案

> 两个 P0：① 让「改写 / 优化已有作品 / 只润色」三条工作流的稿子在右栏看得见；
> ② 纸面从只读改成可双击就地编辑。2026-07-31 定稿。
>
> 前作：[`2026-07-29-writing-live-preview-design.md`](2026-07-29-writing-live-preview-design.md)
> —— 本方案修的正是它遗留的 H-2，并推翻它「明确不做纸面手动编辑」那一条。

## 目标

| | 现状 | 改完 |
|---|---|---|
| **P0-1 覆盖面** | 改写 / 优化已有作品 / 只润色跑完，右栏恒显「还没有正文」 | 三条都能在右栏看见稿子，排版皮肤也对 |
| **P0-2 手动编辑** | 纸面只读，改一个错别字也要跑一轮 AI 改写 | 双击段落就地改源码，Esc 取消，失焦存盘，可撤销 |

## 明确不做（本轮）

- **一稿多平台（`serialize.md`）仍不接管**。它产出的是同一篇的公众号版 / 小红书版 /
  知乎版**多个平行版本**，不是一篇文章的多个小节；塞进 `drafts/` 会被纸面首尾相接拼成
  一篇，那是错的。它真正需要的是「平台切换器 + 多文档源」，属于另一个功能。
  本轮只把前作里那张误导人的覆盖范围表改对。
- **版本历史不落磁盘**。撤销栈只在内存、关窗即失。真正的 `.history/` 快照要配目录清理
  策略与历史浏览 UI，是独立功能。
- **不做重做（redo）**。撤销错了自己再敲一遍。
- **P1 三项（配图 / 质检面板 / 字数进度）不在本轮**，另开一份设计。

## P0-1 · 让三条工作流的稿子落到右栏扫得到的地方

### 现状核实（比前作 H-2 记的更细）

| 工作流 | 稿子实际落在 | 右栏 |
|---|---|---|
| 主管线三体裁 | `<项目>/drafts/*.md` | ✅ 已接管 |
| 去AI化 `de-ai` | `<cwd>/写作/<标题>-去AI版.md` | ✅ 已接管（单文件模式） |
| 职场写作 `workplace-writing` | `<cwd>/写作/<标题>.md` | ✅ 已接管（单文件模式） |
| 改写 `rewrite` | `<项目>/output/rewrite.md` | ❌ 恒空 |
| 优化已有作品 `optimize-existing` | 「改动落 `output/`」，实际路由到上下两条 | ❌ 恒空 |
| 只润色 `polish-only` | **压根没规定落点**，也不建项目 | ❌ 完全不接管 |
| 一稿多平台 `serialize` | `<项目>/output/<主题>-<平台>.md` 多份 | ❌ 恒空（本轮不管） |

根因：`electron/main/core/writingProject.ts` 的 `sectionDir()` 对 project 模式硬编码
`<projectDir>/drafts`。`project_manager.py init` 会把五个子目录都建好，所以 `drafts/`
存在但恒为空 → 纸面永远停在「还没有正文」；`isWritingInProgress` 也因为要求
`${dir}/drafts/` 前缀而恒假，连进度骨架都不出。

### 决策：改工作流落点，前端一行不动

三个候选方向（前作 H-2 列的）里选「让工作流改落 `drafts/`」。理由：

- **语义上反而更顺**。主管线本来就是「`drafts/` = 正在打磨的正文，`output/` = 定稿与
  导出物（.docx / .html）」。改写稿、润色稿正是「正在打磨的正文」，它们落 `output/`
  才是跑偏。这不是破坏语义，是把跑偏的三条掰回主管线的语义。
- **另外两个方向各有硬伤**：让前端回退去扫 `output/` 要引入一层启发式规则（既有原稿又有
  改后稿、还有多平台版本时显示哪份？）——这种「猜」日后必然猜错；统一走单文件模式则会让
  同一篇稿子在项目里和 `写作/` 下各存一份，两边会漂，违反「磁盘是唯一真相源」。

### 落点分界：建项目的走 `drafts/`，轻量快道走单文件

`polish-only` 是**轻量快道**——用户丢一篇稿子进来直接润，不跑 `project_manager.py init`。
强制它建项目等于让快道名存实亡。所以它沿用 `de-ai.md` 已跑通的单文件通道。

这不是新增概念，而是把已经存在的分界说清楚：

| 类别 | 工作流 | 落点 |
|---|---|---|
| 建项目（要留档原稿、要跑质检脚本） | 主管线三体裁、改写、优化已有作品 | `<项目>/drafts/` |
| 轻量快道（不建项目） | 去AI化、职场写作、只润色 | `<cwd>/写作/<标题>.md` |

> **「优化已有作品」是例外——它是路由器，不是终点**：`optimize-existing.md` 无条件建项目、
> 把原稿存进 `<项目>/sources/`（这是为了留档原稿、跑 `ai_slop_checker.py` 等质检脚本，
> 这部分不看用户选哪一档，所以固定建项目）。但它自己**不产出成稿**，Step 5 确认档位后
> 会把用户路由到 `rewrite.md` 或 `polish-only.md`，成稿落点跟着接手的工作流走：
> **标准优化 / 深度改写**档路由到 `rewrite.md`，落 `<项目>/drafts/`（与建的项目同一个目录，
> 落点一致）；**轻度润色**档路由到 `polish-only.md`，落 `<cwd>/写作/<标题>-润色版.md`
> ——这是轻量快道的落点，跟 `optimize-existing.md` 建的项目目录**脱钩**，`sources/` 里的
> 原稿和最终成稿因此分居两处。这是刻意的产品取舍（不在本任务改动范围），本表把它记清楚，
> 避免下一个人照着「优化已有作品 → drafts/」的简化认知去判断，重蹈前作 H-2 的覆辙。

### 具体改动（全部在 `skills/writing/`，`apps/studio` 零改动）

| 文件 | 改什么 |
|---|---|
| `workflows/rewrite.md` | Step 4 标题与正文里的 `<项目>/output/` 改为 `<项目>/drafts/`；Step 5 复检命令的路径同步改；检查点「改写稿在 output/」改为 drafts/ |

| `workflows/polish-only.md` | 新增 Step 0「落单文件」：润色稿写到 `<cwd>/写作/<标题>-润色版.md`（目录不存在先建），照抄 `de-ai.md` 那一段的写法与理由 |
| `SKILL.md` | 独立工作流索引表里三条的描述若提到落点，同步改 |
| `docs/superpowers/specs/2026-07-29-writing-live-preview-design.md` | 覆盖范围表改对；H-2 标记为「已由本方案解决」，并注明 serialize 仍不覆盖 |

### 附带修掉：排版皮肤回退错档

右栏的排版皮肤（公众号手机窄栏 / 小说分页 A4 / 文章 / 职场）来自 `spec_lock.md` 的
`- genre:` 行，解析不到时回退 `workplace`（见 `electron/shared/writing.ts` 的
`GENRE_LINE` 与默认档注释）。而改写 / 优化**不走策划八项、通常没有 `spec_lock.md`**
→ 拿一篇公众号推文来优化，右栏用职场公文的排版显示它。

补法：这两条工作流本来就有一张「看原文像什么 → 定 `genre`」的判断表
（`rewrite.md` 第 61 行那张），让它们判完之后顺手写一份最小契约：

```markdown
## 体裁
- genre: wechat
```

段名 `## 体裁` 与字段名 `genre` 必须与 `update_spec.py` 认的那套一致（八个固定段名之一），
否则后续要改契约时脚本认不出。小说改写场景本来就要逆向补完整 `spec_lock.md`
（`rewrite.md` 第 95 行），那条不变，这里补的是其余体裁的最小版。

## P0-2 · 纸面双击就地编辑

### 为什么推翻前作的「不做」

前作把它列进「明确不做」，理由是「少一整套块级 contentEditable + 失焦写盘 + 与 AI 写入
抢文件的时序」。这次推翻它，是因为实际用下来「改一个错别字也要跑一轮 AI」的代价比预估
的高得多。但前作担心的那个时序问题是真的，本方案必须正面回答它——见下面的「锁」与
「乐观锁基准」两节。

### 编辑形态：点哪段改哪段，改的是 Markdown 源码

```
【只读态】                      【双击第二段后】
  一、开场                        一、开场          ← 仍是排好版
  那天晚上他没回家。              ┌──────────────────┐
  雨下得很大。                    │那天晚上他**没回家**。│ ← 变输入框，显源码
                                  └──────────────────┘
                                  雨下得很大。      ← 仍是排好版
```

不做所见即所得（在排好版的字上直接改）的原因：那要把富文本反向转回 Markdown，加粗 /
列表 / 链接在来回转换里很容易跑掉，是个经典的坑，工作量比源码编辑大一个量级。
不做整节切换「阅读 / 编辑」的原因：改一个错别字也要盯着一屏源码找。

### 状态机

```
只读 ──双击──► 编辑中（textarea 显本块源码）──点别处 / Cmd+Enter──► 存盘 ──► 只读
                     │
                     └──Esc──► 丢弃修改，回只读
```

- 编辑框下方一行提示：`Esc 取消 · 点击别处保存`。
- **内容与进入编辑时逐字节相同 → 直接回只读，不写盘**。避免无意义的 IPC 与无意义的
  撤销栈条目（否则用户点开看一眼再点走，也会占掉一格撤销额度）。
- textarea 高度随内容自适应，不出现滚动条套滚动条。
- **双击另一个块 = 先存当前块、再进入新块的编辑**（不是「取消当前块」）。理由：用户连着
  改相邻两段是常态，若第二次双击把第一段的改动丢掉，损失是静默的、他不会发现。存盘失败
  时则停在原块并报错，不跳走——否则错误提示会伴随着焦点转移一起被忽略掉。
- 同一时刻只有一个块处于编辑态。

### 锁：AI 正在写时不能进入编辑

判据复用现成的 `useWritingInProgress()`（「这一轮有没有往当前文档源的 `drafts/` 落字」，
**不是**会话级 `streaming`——后者在 AI 跑无关 shell 时也为真）。为真时：

- 块双击无反应，纸面顶部挂一条提示说明原因。这条提示与已有的「刷新文稿失败」黄条同为
  `sticky top-0`，两条可能同时成立——按「刷新失败」优先显示（那条关乎「你看的内容是不是
  最新的」，比「现在不能编辑」更要紧），不叠成两行占掉纸面顶部。
- **已经在编辑中的块不踢出**。强行退出会直接丢掉用户正敲的字；改为在编辑框上方加一条
  黄条「AI 正在改这篇稿子，保存时可能冲突」，真冲突了由乐观锁兜住。

这条锁从根上消掉了绝大多数「抢文件」场景——写作流水线本来就是 AI 写完一节才轮到人看。

### 乐观锁基准取哪一刻（最容易写错的一处）

**取「进入编辑那一刻」那一节的 `mtimeMs`，不是存盘那一刻的。**

理由与 `stores/writing.ts` 里 `baseMtimeMs` 字段那段注释完全同构，此处复述是因为这是
两条通道共同的地雷：轮询每 2s 把 `sections` 连同 `mtimeMs` 从盘上刷一遍。若基准取存盘
那一刻的最新值，下面这条链会静默毁掉正文：

```
T0  进入编辑（基于 M0/m0，用户看到并开始改的是 M0）
T1  AI 又改了这一节 → 盘上变 M1/m1 → 轮询把 store 刷成 M1/m1
T2  用户点别处存盘 → 拿 m1 当基准 → 主进程比对相等、放行
    → 把基于 M0 编辑的内容拼进 M1 的错误位置，无冲突提示、不可逆
```

也就是说「用户编辑期间文件被改过」——锁最该拦的那个场景——恰恰被漏掉，锁实际只覆盖了
「最后一次轮询到写盘」那 2 秒。基准必须与用户看到的那一版**同源同刻**。

### 代码落点

**不新增任何 IPC**。手动编辑与 AI 改写的落地是同一条链，只是「新内容从哪来」不同：

```
AI 改写：  AI 回哨兵包住的新文字 ─┐
                                  ├─► spliceBlocks 换块 ─► writingWriteSection ─► 写盘
手动编辑：  用户在 textarea 敲的字 ─┘        （带 expectedMtimeMs 乐观锁）
```

| 文件 | 改动 |
|---|---|
| `src/chat/lib/writingEdit.ts`（新） | 纯函数：块替换、「内容是否真的变了」判定。放 `src/chat/lib/` 是因为 `bun test` 的扫描目录包含它，纯函数自动进测试范围 |
| `src/chat/components/workspace/WritingPaper.tsx` | 块从纯展示变成「只读 / 编辑中」两态；新增 `onEditBlock` 回调，与现有 `onRevise` 对称（省略时纸面仍是纯只读，不冒出编辑能力） |
| `src/chat/components/workspace/WritingDocPanel.tsx` | 实现 `onEditBlock`：换块 → 写盘 → 更新 store → 压撤销栈。**与现有 `applyRevision` 的写盘/冲突处理大量重合，抽出公共函数供两条通道共用**——两处各写一份必然在冲突文案与 store 更新顺序上漂 |
| `src/chat/stores/writing.ts` | 新增 `undoStack` 与 push / pop 两个 action；`setSource` 里一并清空 |

`WritingDocPanel.tsx` 现为 604 行，改完约 700 行，未到仓库约定的 ~1500 行拆分线，不拆目录。

### 撤销栈

```ts
undoStack: { sectionName: string; markdown: string; mtimeMs: number }[]
// 存的是「改之前」那一节的完整内容
```

- **两条通道共用**：手动编辑存盘成功、AI 改写点「应用」成功，都往栈里压一条。用户心里
  只有一个「后悔」的概念，不该因为改动来自哪条通道而行为不同。
- 上限 20 步，超出丢最老的。只在内存，不持久化。
- **撤销 = 把旧内容再写一次盘**，同样走 `writingWriteSection` 带乐观锁，
  `expectedMtimeMs` 取**当前** store 里那一节的 `mtimeMs`（撤销的语义是「把它现在变回
  旧样子」，基准就是现在）。若这中间 AI 又改过，撤销同样被拦下并提示，不静默覆盖。
- 换源（`setSource`）清空栈：旧稿的 `sectionName` 对新稿没有意义，留着会往错的文件里写
  内容——这类跨文档串台是不可逆的正文损坏。
- 顶栏在栈非空时出现「撤销上一步」，悬停显示将撤销哪一节。

### 边界情况裁定

| 情况 | 处理 |
|---|---|
| 把输入框清空 | 视为**删除这一段**，不弹确认框——有撤销栈兜底 |
| 输入框里敲了空行 | 存盘后 `splitBlocks` 自然切成两块，纸面变两段。Markdown 的正常语义，不拦 |
| 编辑标题 / 表格 / 围栏代码块 | 无特殊逻辑，源码编辑天然支持所有块类型 |
| 编辑中的选区改写气泡 | 隐藏。同一时刻只走一条修改通道，避免两套定位打架 |
| 双击选中词导致冒出气泡 | 进入编辑前主动清除浏览器选区（`window.getSelection()`） |

### 样式纪律（仓库铁律，容易踩）

- 编辑用的 `<textarea>` 与「撤销上一步」按钮都要能扛住 canvas 侧的裸元素 reset。
  按 CLAUDE.md：canvas 的 `textarea`/`button` reset 带 `:where(:not([data-slot], .chat-app *))`
  守卫，写作面板在 `.chat-app` 下，天然豁免；但**若将来把编辑框 portal 到 body 就会脱离
  豁免**，那时必须补 `data-slot`。本轮不 portal。
- 顶栏新增的撤销按钮落在根 layout 的 46px 拖拽带内，必须包在已有的
  `[-webkit-app-region:no-drag]` 组里（现有导出下拉已经在那一组，跟着放即可），
  否则点击会被窗口拖拽吞掉。

## 错误处理

一条总原则：**冲突一律不覆盖**。宁可让用户重敲一遍，也不静默毁掉磁盘上的正文——正文
损坏不可逆，重敲只是麻烦。

| 失败 | 用户看到 | 数据安全性 |
|---|---|---|
| 乐观锁拦下（编辑期间被 AI 或外部改过） | 「这一节刚被改过，你的改动未生效。已刷新到最新内容，请重新修改。」纸面刷成盘上最新版 | 安全，旧版未覆盖新版 |
| 文件已不存在（被删 / 改名） | 「这一节的文件已不存在，改动未生效。」——**不能复用上一条文案**，那会让用户按提示再操作一次、再撞一次同样的墙 | 安全 |
| 写盘失败（权限 / 磁盘满） | 「写入失败：<原始错误>」 | 安全，main 侧是写临时文件再原子替换，失败不留半截文件 |
| 撤销时撞冲突 | 同第一条，撤销不生效 | 安全 |
| 轮询读盘失败 | 已有的黄色提示条「刷新文稿失败，下面显示的可能不是最新内容」 | 安全，2s 后自愈 |

5. Esc → 内容不变，文件 mtime 不变。
6. 清空一段 → 该段消失 → 点「撤销上一步」→ 回来了。
7. AI 正在写的时候双击 → 进不去，有提示。
8. **冲突验证**：进入编辑后用外部编辑器改同一个文件并保存 → 再点别处存盘 → 出冲突
   提示，且**外部的改动没有被覆盖**。

第 8 条是本轮最该验的一条——乐观锁基准若取错，前七条全绿它也会静默毁数据。
