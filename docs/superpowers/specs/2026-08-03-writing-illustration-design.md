# writing skill 插图能力设计方案

> 给 `skills/writing/` 补上配图能力：公众号氛围配图走 AI 生图、信息图走 mermaid，
> 复用提案（proposal）功能已跑通的出图 / 审阅链路。2026-08-03 定稿。

## 目标

写作技能目前只产文字。本设计让它能**在策划阶段就规划配图、在写作阶段顺手产图、
在预览里看得见、在导出时带得走**，覆盖两类需求：

- **公众号文章配图** —— 封面图 + 正文氛围配图（意境、场景、情绪）
- **信息图 / 示意图** —— 流程、对比、结构（偏说明性）

**明确不做**（本轮排除，理由见「不做什么」一节）：小说插画、联网找图、
一次出多张候选图、把用户自己的图片编排进正文。

## 为什么不是「加个出图脚本」就完事

配图不是在正文末尾追加一个 `![]()` 那么简单。写作技能是一条串行流水线，
图必须**和内容一起被规划**，否则会退化成「写完硬塞几张装饰图」——这正是
AI 生成内容最典型的廉价感来源。所以本设计的重心在契约层（第 ⑨ 项确认 +
配图手册），而不在出图 API。

同时，这个仓库里已经有一套**跑通了的**出图链路（提案功能），从 AI 留指令
到审阅落位到导出嵌图五个环节齐全。本设计的工程部分几乎全是「把写作接进这条
现成的链路」，而不是造第二条——仓库有过同一逻辑写两份、随后静默漂移的事故
（`writingWechat.ts` 的头注释专门记了这条教训）。

## 一、现状缺口（实施前的事实核查结果）

| # | 缺口 | 核查依据 |
|---|---|---|
| 1 | 技能完全不知道配图这回事 | `skills/writing/` 129 个文件中零处提及图片 |
| 2 | 没有出图触发链路 | 提案侧有 `proposalGenImageFire.ts` + `GenImageDirectiveCard` + `ProposalImageReview`，写作侧无对应物 |
| 3 | 图出了也显示不出来 | Electron 渲染进程不能直接 `<img src="/abs/path">`；现有三个本地资产协议（`kbasset` / `proposalasset` / `pptasset`）守的根都不含写作项目目录 |
| 4 | 三条导出链都不认图 | `writingWechat.ts` 无任何 `!\[\]` 处理；`export.py` 同（前者是后者的 TS 移植）；`WritingDocPanel.tsx:578` 注释白纸黑字写着「写作体裁不支持 mermaid 代码块」，PDF 导出给预渲染 mermaid 传了 `undefined` |
| 5 | 质检会被图片行带偏 | `writing_utils.strip_markdown` 不剥图片语法 `!\[\]\(\)`（**但已剥围栏代码块，故 mermaid 本来就免疫**，见第五层） |
| 6 | 项目目录没有放图的地方 | `project_manager.py` 的 `SUBDIRS` 只有 `sources/ analysis/ drafts/ reviews/ output/` |

**一个正面发现**：写作预览右栏用的是 `AssistantMarkdown`，而它**已经内置了
```mermaid 围栏 → 渲成图**的逻辑（`AssistantMarkdown.tsx:370`）。所以 mermaid
在预览里本来就能显示，缺的只是导出那一环。这是「信息图走 mermaid」这条路线
成本最低的直接原因。

## 二、两条腿：为什么信息图不用 AI 生图

| 图的类型 | 产法 | 为什么 |
|---|---|---|
| 氛围 / 封面 / 场景图 | AI 生图（gpt-image 系列） | 要的是感觉，模型强项 |
| 流程 / 对比 / 结构图 | AI 写 mermaid | 生图模型画不好字：中文标注必糊必错字，发公众号是硬伤。mermaid 里的字是**真文字**，清晰、可改、可复制 |

曾评估过第三条路（像 ppt-master 那样让 AI 直接写 SVG）：视觉自由度最高，
但预览与导出都要新建渲染链路，工程量明显大一截，且写作场景对信息图的美术
要求远低于 PPT。本轮不做，若日后公众号信息图审美不够再升级——mermaid 与
SVG 在正文里都是围栏代码块，届时替换不影响契约层。

## 三、架构：五层

### 第一层 · 技能契约（决定「配不配图、配什么图」）

**① 八项确认扩为九项。** Step 4 新增第 ⑨ 项「配图方案」，属**实现层**
（由锚点重推，不是独立锚点）。落进 `spec_lock.md` 新段 `## 配图`：

```
- image_plan: none | cover-only | inline
- image_count: 3
- image_style: 极简线条插画
```

- `image_plan` —— 不配图 / 只配封面 / 正文内也配。
- `image_count` —— 张数上限。**这是防失控的第一道闸**（第二道在 app 侧的
  自动触发上限），生图是要花钱的。
- `image_style` —— 生图风格。它是**创作性字段**，因此适用 SKILL.md 已有的
  硬规则：必须给 ≥3 个候选、每个带一句「选它是什么效果」，由用户拍板。
  `image_plan: none` 时本字段留空、不必问。

> ⚠️ **同步改 `update_spec.py` 的 `IMPACT_MAP`**（注意实际常量名是 `IMPACT_MAP`，
> 不是 `SECTION_IMPACTS`）。核查澄清：`set_field` 对未登记的段**照样能改**
> （段不存在时会在文件末尾补一段），所以这不是功能阻塞，而是**提示缺失**——
> 未登记的段改完不会打印「影响范围」那一行，用户拿不到「哪些已写章节需要回改」
> 的提醒。登记文案：「配图方案变更影响已写章节里的出图指令块，需复核受影响
> 章节的配图位」。

**② 分节大纲带配图位。** `design_spec.md` 的分节大纲里每节增加一行
「本节配图：无 / 氛围图（图说是什么）/ 信息图（要画哪几个要素）」。
配图位与内容一起规划，是「图不是装饰」这条原则的落地方式。

**③ 新增配图手册 `references/illustrator.md`。**

**不新增第五个角色。** 四角色流水线（策划 → 写手 → 审校 → 润色）的边界是
整个技能的骨架，新增角色会打破「一棒交一棒」的串行契约。配图仍由**写手**在
写到那一节时顺手留出图指令；本手册是写手的参考资料，不是岗位说明书。写手在
Step 6 的「每节动笔前固定动作」里增加一条：`image_plan != none` 时读一次
`references/illustrator.md`。

手册内容：

- **什么该配图**：配图是替读者省认知，不是装饰。判据——这张图能否比同等篇幅
  的文字更快说清一件事？不能就不配。
- **两条腿的判据**：能一句话说清的关系 / 流程 / 对比 → mermaid；讲氛围、
  场景、情绪、封面 → 生图。
- **生图提示词写法**：封面比例、中文标签少而大、不要水印、不要与内容无关的
  装饰。（提案侧的 `buildGenImagePrompt` 已有一套「统一风格约束」拼接法可参
  照，但写作的风格来自契约的 `image_style`，不能照抄提案写死的「蓝色系商务
  信息图」。）
- **mermaid 在公众号的限制**：手机屏窄，横向图会被压成蚂蚁。因此节点数封顶、
  方向优先竖排（`graph TD`）、单节点文字尽量短。
- **图说（caption）写法**：图说要有信息增量，禁止「如图所示」这类零信息说明。
  图说同时是 `![图说](路径)` 的 alt 文字与导出时的图片标记。

**④ 导出前加「图片就位闸」。** Step 9 导出前逐个检查正文里 `![]()` 指向的
文件真实存在，缺图**停下报清单**（列出缺哪几个文件、应该放在哪），而不是导出
一份带碎图的稿。这条照抄 ppt-master 的 Image readiness GATE——它的注释写明了
理由：下游导出器不在这一层检测缺失，带着缺口继续跑只会产出引用损坏的成品。

**⑤ 项目目录加 `images/`。** `project_manager.py` 的 `SUBDIRS` 增加
`"images"`，`README.md` 模板与 `validate` 的目录检查同步。

### 第二层 · 出图与审阅（app 侧）

**指令块格式直接复用提案的 `genimage`**，不新造语法：

````
```genimage
图说: 一个人在深夜的便利店窗边写字
暖黄灯光，窗外下雨，人物背影，安静的氛围
```
````

解析器 `electron/shared/proposalGenImage.ts` 位于 shared 层，写作侧**直接
import，不复制**。字段结构（图说 + 构图描述）与写作需求完全同构。

> 命名取舍：函数名带 `proposal` 前缀而被写作复用，读起来别扭。但**本轮不改名**
> ——改名要动提案侧全部调用点，与本功能无关，属于「不相关的重构」。若后续两边
> 都稳定了，再单独一次改名提交。

**⚠️ 写作与提案的运行模型不同，触发与落地都不能照搬。** 提案的正文活在内存
里（zustand store 的 sections），有明确的「落节」事件可挂；**写作的正文是磁盘
上的 `drafts/*.md` 文件**，右栏靠 `useWritingPoll` 定时重扫（比对
`name:mtimeNs:size` 签名，变了才重读）。两处差异必须分别处理：

- **触发时机**：没有落节事件可挂，改为**在轮询发现 sections 变化之后**扫新
  指令块。两道保护缺一不可：
  1. **幂等**：沿用提案的 job key 机制（键已存在即跳过）。轮询每几秒跑一次，
     没有幂等就是每一轮重复出图、重复烧钱。
  2. **稳定后再触发**：AI 还在写这一节时文件仍在变，此刻的指令块可能是半截的
     （围栏未闭合、构图描述只写了一半）。因此只在**该节签名连续两轮不变**、
     或**本轮对话已结束**（`handleWritingTurnEnd` 同一时机）时才发起。提案侧
     靠「落节」天然规避了这个问题，写作必须显式做。
- **重开会话不自动发起**（防重复烧生图费），重建出的指令块渲染成「点此生成」
  的手动卡——与提案侧 `autoFireProposalGenImages` 的取舍一致。
- **自动触发上限**：沿用提案的 `MAX_AUTO_FIRE_PER_SESSION = 5`，超限的指令块
  留成手动卡，用户看得见、点一下也能生成，不静默丢。这是防「提示词失灵导致
  AI 输出几十个指令块」的兜底。
- **审阅卡**：复用 `GenImageDirectiveCard` + `ProposalImageReview` 的呈现。
  图出完先进审阅卡，用户点「应用」才把指令块**原地替换**成
  `![图说](相对路径)`，不满意可重出或丢弃。
- **应用即写盘，且必须走已有的乐观锁**：提案的「应用」改内存，写作的「应用」
  要把替换后的正文**写回 `drafts/*.md`**。这条路径已经存在——手动编辑与 AI
  选区改写共用的 `commitSection` + `baseMtimeMs` 乐观锁（防「AI 正在写这一节 /
  用户在外部编辑器改了同一文件」时互相覆盖）。配图落位必须复用它，**不得另开
  一条直接写盘的路**，否则会绕过并发保护、静默丢草稿。

### 第三层 · 图存哪、怎么显示

**存哪：写作项目自己的 `<项目>/images/`**，不是提案那种
`<userData>/proposal-drafts/`。理由：

1. 写作项目本来就建在用户能看见的磁盘目录里（`$(pwd)/projects` 或
   `$HOME/writing-projects`），图跟着项目走，整个文件夹搬走图不丢。
2. 与 ppt-master 的项目内 `images/` 一致。
3. 纯命令行使用（无 app）时也能自然落盘。

**正文里写相对路径** `![图说](../images/xxx.png)`（`drafts/` 与 `images/`
是兄弟目录）。渲染与导出时用项目根拼回绝对路径。

**怎么显示：新增 `writingasset://` 协议。** `localAssetProtocol.ts` 的注册
工厂支持两种守卫模式：单一固定根（`kbasset` / `proposalasset` 用），或调用方
传入白名单谓词（`pptasset` 用——它服务的同样是「任意用户目录下的项目」，
main 进程无法枚举所有项目根）。写作照抄 `pptasset` 的白名单写法：扩展名
白名单 + 路径必须含 `/images/`。

> 诚实记录一个事实：`isPptAssetPath` 现有的白名单已包含 `/images/` 段与图片
> 扩展名，写作项目的图**技术上已经能被 `pptasset://` 服务**。仍然新增一个
> scheme，理由是命名语义与爆炸半径——让写作的图走一个叫 `pptasset` 的协议，
> 下一个读代码的人会误判归属；且日后收紧任一侧的白名单不会误伤另一侧。
> 代价是一个约 30 行的新文件 + 在 `index.ts` 的 `registerSchemesAsPrivileged`
> 里登记（**必须在 app ready 之前**）。

渲染侧在 `AssistantMarkdown` 的 `img` 覆写里增加一条链式判定（现有链是
`kbasset` → `proposalasset`，新增 `writingasset`）。

### 第四层 · 导出（三条链都要补）

| 格式 | 要做什么 | 说明 |
|---|---|---|
| **docx** | 复用 `proposalDocx.ts` 的 `imageParagraphs` | 现成，注意它已有「非可嵌格式降级为文字占位」的逻辑，与预览侧共用同一个谓词 |
| **PDF** | 把 `WritingDocPanel.tsx:578` 那个写死的 `undefined` 换成真的预渲染 mermaid 图 | 一行量级；`renderProposalPdfHtml` 第三参数本就是为此设计的 |
| **公众号 HTML** | `![]()` → `<img>`，图片一并复制到 `output/images/`，并在 HTML 顶部生成插图提示 | 有平台限制，见下 |

**公众号那条链的平台限制（不可绕过，只能降级）**：微信编辑器粘贴 HTML 时会
丢弃所有指向本地文件的图（它只认已上传到微信服务器的图），且不支持 data URI。
因此**做不到「粘一次全带图」**。降级方案：

1. 导出时把用到的图复制进 `<项目>/output/images/`；
2. HTML 里保留 `<img>` 元素（本地相对路径），位置正确；
3. HTML 顶部生成一段提示块：「本文共 N 张图，已放在 output/images/，请在
   公众号编辑器里按标记位置逐张插入」，并逐张列出「第 k 张 · 图说 · 文件名」；
4. **封面图单独标注**——公众号封面在编辑器里是独立上传项、不进正文，
   `image_plan: cover-only` 或首图为封面时，提示里把它单列。

`export.py`（Python，命令行侧）与 `writingWechat.ts`（TS，app 侧）是同一套
转换逻辑的两份实现，**本次改动必须两边同步**，否则命令行导出与 app 导出会
产出不同的 HTML——这正是 `writingWechat.ts` 头注释警告过的漂移场景。

### 第五层 · 质检不被图带偏

**范围比初稿小，因为一半已经免疫。** 核查后确认：`writing_utils.strip_markdown`
已经会剥掉围栏代码块（`_FENCE` 开关跳过整块），而 `ai_slop_checker.py:92` 与
`readability_check.py:53` 都调用了它——**mermaid 源码本来就不进统计**，无需
改动。

真正的缺口只有一个：**图片语法 `![图说](路径)` 不在剥离范围内**。它会被当成
一个极短段落进入统计，污染两处：平台合规检查的「段落长度分布」（图说行远短于
正文段），AI 味检测的「结构均匀度」（多一批异常短段拉高方差）。图配得越多，
两个分数越假——**质检失真比没有质检更危险**，因为它给出的是虚假的安全感。

做法：在 `strip_markdown` 里增加一条——先把每行的 `!\[...\]\(...\)` 整体删掉，
删完若该行变空则整行丢弃。这样对「图独占一行」（常态）与「图夹在句子里」
（罕见）都正确，且不误伤普通链接 `[文字](url)`（图片语法有前导 `!`）。

## 五、验收标准

- `bun run typecheck` 通过（本仓库无 ESLint，类型检查是唯一的全局自动防线）
- `bun test`（在 `apps/studio` 下跑）**不新增失败**。注意**不是**「全绿」——
  该仓库有 6 个既存失败，把验收写成全绿会导致无法判定本次改动是否引入回归
- `skills/writing/tests/` 的 pytest 通过（现有 9 个测试文件，本设计新增的
  纯函数——剔除函数、契约新段解析、导出认图——都要补测试）
- 端到端手动走查一条：写一篇带 1 张封面图 + 1 张流程图的公众号文章，
  完整走「策划确认配图 → 写作留指令 → 出图 → 审阅应用 → 预览看得见 →
  导出带图且提示正确」

## 六、风险与取舍

1. **生图要花钱。** 两道闸：契约里的 `image_count`（策划期定）+ app 侧自动
   触发上限 5（运行期兜底）。重开会话不自动重出，是第三道。
2. **公众号必须手工插图。** 平台限制，不可绕过。设计目标降为「把手工步骤压到
   最低、且不出错」：图按位置留在 HTML 里、文件按序号命名、提示块逐张列明。
3. **审阅卡抽共用可能改坏提案。** 那两个组件现在与提案的 store 和文案耦合。
   纪律：**先纯重构、验证提案侧行为不变、给用户看过，再接写作**——不把重构
   与新行为塞进一次改动（这是用户已确认的既有偏好）。
4. **`spec_lock.md` 加段是有传染性的改动。** 段名同时被 `update_spec.py`、
   `continuity_check.py`、`readability_check.py` 读取。新增段只增不改既有段名，
   且新增后要跑全套 pytest 确认三个读取方都不受影响。
5. **`export.py` 与 `writingWechat.ts` 双份实现。** 本次两边同步改，并在两侧
   注释里互相指认，降低下次漂移概率。
6. **轮询触发比事件触发更容易出重复与半截。** 这是写作与提案最大的架构差异，
   也是 P1b 最可能出 bug 的地方。三道防线：job key 幂等、签名稳定判据、
   自动触发上限。走查时要专门试「AI 正在写这一节时右栏是否误触发」。
7. **已知的既有残留会放大配图的风险**（记录在案，本轮不修但要避开）：
   `beginEdit` 在一次写盘在飞的窗口内连点两块会乱序覆盖。配图落位若与手动
   编辑并发，可能撞上同一个窗口——因此配图落位必须走 `commitSection`
   同一条路径，不要新增第二个写盘入口，否则这个残留会从「两块」扩散成
   「编辑与配图」。

## 七、不做什么（本轮明确排除）

| 排除项 | 理由 |
|---|---|
| 小说插画 | 用户明确不需要；且小说插画对人物一致性要求高（同一个角色多张图要长得一样），需要参考图 / 角色锁定机制，是另一个量级的问题 |
| 联网找图 | 版权与质量都不可控；ppt-master 的 `image_search.py` 依赖用户自配图库 key，对桌面端终端用户不友好 |
| 一次出多张候选 | 出图成本与等待时间翻倍，审阅卡也要重做。若单张重出的体验够用就不做 |
| 把用户自己的图编排进正文 | 提案侧已有上传通道可参照，但写作场景需求弱，等有真实需求再补 |
| 信息图走 AI 手绘 SVG | 见「两条腿」一节：工程量大一截，mermaid 先够用 |
