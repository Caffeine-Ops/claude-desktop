# 生产配置：给「审标书」加一张场景卡

这是一份**照着做**的操作文档，写给要在生产管理台上手动配置的人（不需要懂代码，跟着步骤填表格就行）。它解决的是一个具体问题：客户端里新加了「审标书」这个技能，但**登录用户在正常使用里目前还看不到它**。往下看会解释为什么，以及怎么让它出现。

---

## 1. 这份文档解决什么

Claude Desktop 客户端聊天界面空白状态时，侧栏会有一排「场景卡」（制作PPT / 处理表格 / 写方案……点一下就能直接开始对应的工作）。这排卡片其实有**两个不同的来源**，用哪个来源取决于你有没有登录：

- **来源 A：客户端代码里写死的默认表**。这是打包进安装包里的一份固定清单，只有在**未登录 / 断网 / 全新安装还没连上后台**的情况下才会用到它。这次的改动已经把「审标书」加进了这份默认表——所以这部分用户已经能看到新卡片，不用你做任何事。
- **来源 B：后台（管理台）远程下发的一份配置**。这是**已登录用户实际看到的那一份**。客户端登录后会去后台要一份场景卡清单，要到了就用它，要不到（后台从没配过）才退回用来源 A 的默认表。

问题就出在这里：**如果生产后台已经配置过场景卡目录（哪怕只有原来那几张卡，没有审标书），已登录用户看到的就是后台那份旧清单，里面没有审标书**。默认表加了新卡片，对已登录用户根本不生效——因为他们压根不读默认表。

所以要让已登录用户也能看到「审标书」，**必须去后台管理台里手动把这张卡加进远端配置**。这就是这份文档要带你做的事。

---

## 2. ⚠️ 动手前必读——这条纪律不能跳

### 2.1 后台保存是「整份覆盖」，不是「往里加一条」

这一条是本文档里最重要的一句话，务必先理解：

管理台保存配置用的是一个叫 `PUT`（可以理解成"用我这次提交的内容，把服务器上原来那份整个换掉"，跟"追加一条"完全不是一回事）的操作。**你这次提交的整份内容，就是保存后线上的整份内容**——不是"把审标书这一条加进已有的清单里"，而是"用你手上这份清单，把线上原来的清单整个覆盖掉"。

打个比方：这就像改一份共享文档，如果你不是在原文档上加一段话，而是直接把自己电脑里存的一份旧版本整个复制粘贴上去覆盖，那么别人在原文档里做过的所有修改（运营改的文案、加过的其他卡片……）**全部会被抹掉，而且线上没有"撤销"按钮找回来**。

所以正确的操作顺序永远是：

1. **先把线上现在的配置读出来看一眼**（管理台页面本身会显示现有内容，或者用"读取/查看"功能拉一份下来）。
2. **在这份读到的配置基础上，加上审标书这一条**，其他内容原样保留、一个字都不要动。
3. **再保存（提交这次的整份内容）**。

**绝对不要**图省事直接拿本文档第 4 节给的"要填的内容"单独提交一份只有审标书的清单去覆盖——那样会把线上原有的其他场景卡全部冲掉。

### 2.2 `version` 字段不要手填

配置里有个 `version`（版本号）字段，每次保存后台会自己 +1，不需要你去填或改它。你保存完之后可以看这个数字有没有比保存前多 1，来确认这次保存确实生效了（第 5 节会讲怎么用它验证）。

### 2.3 这份配置内容没有在本地测试环境里跑通过

**必须诚实交代一件事**：本来的计划是先在本地测试环境的后台里配一遍、亲眼看着卡片真的出现在客户端里，验证没问题了，再照着同样的步骤去生产环境操作。但这一步没有做成——原因是本地测试后台所在的另一个代码仓库（`cowork_admin`）当时有一处别人没提交的改动（为了绕开构建网络问题手动删掉了 Dockerfile 里的一行配置），按照"不能擅自动别人未提交的改动"的规矩，没有去碰它，所以本地环境没能重新搭起来，这一步就跳过了。

所以现在的情况是：

- **配置的文字内容是可信的**——四条 prompt（用户点卡片后预填的文字）、卡片标题、说明文字，全部是从客户端代码里**逐字**摘出来的，跟客户端里已经在用的内容完全一致，不是凭空编的。
- **但"填进管理台之后卡片真的会正常显示出来"这件事，没有人实际操作验证过。**

也就是说，理论上应该没问题（因为字段格式跟客户端代码定义的类型逐一核对过），但没有人真正跑通过这条链路。请你操作完之后，务必按第 5 节的方法自己确认一遍效果，不要假设"填完就一定成了"。

## 3. 操作步骤

1. 登录生产管理台：`https://cowork.cntcn.com`
2. 进入场景卡配置页面：`/admin/scenario-catalog`（管理台的设置页里应该也有一张入口卡片可以点进去，上面会显示"当前版本 v 几、一共有几个分类"这类信息——如果找不到直接的入口，直接在浏览器地址栏拼上这个路径进去）。
3. 页面打开后，**先看一眼现在已有的内容**（对应第 2.1 节的"先读后改"）。
4. 找到「日常办公」这个分类，在「写方案」这张卡片**之后**，新增一条卡片。
5. 按第 4 节的字段表，把内容逐字填进对应的框。
6. 图标使用文件上传的方式（不要手动粘贴一大串编码），具体见第 4 节的图标说明。
7. 确认其他原有卡片都还在、内容没被改动，然后保存。

（管理台页面具体长什么样子、按钮在哪个位置，这份文档没法替你描述——因为没有人亲眼见过生产管理台这个页面。请对着 `/admin/scenario-catalog` 这个路径自己找，字段名称对上第 4 节的表就行。）

## 4. 要填的内容

### 4.1 基本字段

| 字段 | 值 | 说明 |
|---|---|---|
| 类型（kind） | `skill` | 这是一张会触发"技能"的卡片，不是普通的填充文字卡片 |
| 技能标识（value） | `/claude-desktop:tender-review` | 带前导斜杠，照抄，一个字符都不能错 |
| 卡片标题（label） | 审标书 | 显示在卡片上的名字 |
| 说明文字（description） | 审招标文件，产投标核对清单 | 卡片上的一行小字说明 |
| 图标（icon / iconData） | 见下方「图标」小节 | |
| 二级推荐 prompt（prompts） | 见下方「四条 prompt」小节 | 点开这张卡片后，用户会看到这四条可以直接点的示例问题 |

插入位置：**「日常办公」分类，「写方案」卡片之后**。

### 4.2 图标

图标原始文件在代码仓库里：`apps/studio/public/skill-icons/tender.png`

**请在管理台的"上传图标"功能里直接上传这个原始 png 文件**，让后台自己的图片处理流程去压缩它（管理台通常会自动把图标压成 64×64 像素的 webp 格式，压完大概 2~4KB）。

**不要**去照抄本次任务过程中生成的另一份 JSON 草稿文件（`.superpowers/sdd/2026-08-06-tender-review-skill-integration/scenario-card-payload.json`）里那一长串 `iconData` 编码——那是在本地电脑上用两个小工具（`sips` 和 `cwebp`）手动压出来的等价效果，只是为了让草稿文件更完整、方便你参考格式，**没有走过后台自己的正式压缩流程**，直接照抄有风险。真正操作时用"上传原图，让后台自己处理"这条路径。

**为什么这一步要特别小心（务必读完）**：

整份场景卡配置文件，客户端那边设了一个**硬性上限：1MB**。如果超过这个上限，后果不是"这一张图标不显示"这么轻——而是**客户端会把这次拉到的新配置直接拒收**，只在日志里留一条"keeping cache"，然后**继续用它本地已经缓存的上一份配置**，也就是你上一次保存成功、之前一直生效的那份旧场景卡清单，**不是**前面第 1 节说的来源 A（客户端内置的默认表）。只有从没同步成功过一次的全新安装（本地压根没有缓存文件）才会落到来源 A 的默认表。换句话说，一个图标塞太大，多数已登录用户看到的现象是"这次改动像没保存一样"——旧配置原样留着，不会跳去内置默认表；只有极少数全新安装的用户才会看到内置默认表。这个现象本身也不好排查（两种情况在用户眼里都表现成"没变化"），所以图标必须走管理台的"上传"功能自动压缩，不要手工把没压缩过的大图或者别处复制来的长编码直接塞进去。

### 4.3 四条 prompt（逐字可复制）

点开「审标书」卡片后，用户会看到下面这四条可以直接点击发送的示例问题。请逐字照抄，不要改写、不要润色：

**① 标题：完整审标**

> 帮我审这份【招标文件】：把废标项、评分项、要准备的证明材料、▲ 标识参数、时间节点和合同条款要点全部列出来，每条带原文出处，最后出一份 Excel 核对清单。

**② 标题：只看废标点**

> 帮我看这份【招标文件】里所有会导致废标的条款：资格门槛、实质性要求、投标文件递交规格（形式/份数/封装），每条带原文出处，一条都别漏。

**③ 标题：只看评分项**

> 帮我梳理这份【招标文件】的评分规则：价格分怎么算、商务分和技术分各有哪些得分点、每项多少分、要提交什么才能拿到分，每条带原文出处。

**④ 标题：合同条款要点**

> 帮我看这份【招标文件】里的合同条款：付款方式、质保期、违约责任、验收标准这些中标后才生效的约束，每条带原文出处。

## 5. 怎么确认生效

保存之后，请按下面两步自己确认一遍——**不要假设填完就一定成功了**（原因见第 2.3 节）：

1. **看版本号**：回到管理台入口卡片（或者场景卡配置页面本身），确认 `version`（版本号）这个数字，是不是比你保存前看到的**多了 1**。多了 1，说明这次提交确实被后台接受并生效了；如果没变，说明保存可能没成功，需要重新检查。
2. **用生产账号实际登录客户端看一眼**：拿一个已登录生产环境的账号，打开 Claude Desktop 客户端，进到聊天界面的空白状态，看侧栏「写方案」卡片右边（或旁边）有没有出现新的「审标书」卡片。点开它，确认第 4.3 节那四条 prompt 都在、文字没有错乱或被截断。

两步都通过，才算这次配置真正生效。如果版本号涨了但客户端里没看到卡片，大概率是客户端本地缓存了旧配置还没刷新（可以尝试重新登录或重启客户端），或者配置格式有细节问题，需要再检查一遍字段是否照抄无误。

## 附：一个使用层面的小提醒（不是本次改动引入的问题，但值得告诉用户）

审标书这个技能在处理招标文件时，会在本地一个共享的工作目录（`skills/tender-review/workspace/`）里存放中间分析结果，这个目录是**按文件名**来区分不同任务的，不是按每次对话自动隔离的。也就是说，如果你**先后审两份文件名完全相同**的招标文件（比如两个不同项目都叫「招标文件.pdf」），有可能会错误地复用上一份文件留下的中间分析结果，导致结果对不上。

这是这个技能本身的设计方式，不是这次新加场景卡引入的新问题，但既然会影响到审标书的实际使用效果，值得在这里提一句：**审不同项目的标书时，尽量给文件改个不一样的名字**（比如带上项目名或日期），避免撞车。
